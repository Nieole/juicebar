# 长期缺口：这块产品上还缺什么

**Status:** 长期文件 —— 永远不清空，只增删条目

这份清单讲**产品**上缺什么，由下一个动这块产品的人来读。它不记执行中的岔路——那些在
`.scratch/parking-lot.md`，由 `/settle` 成批结算。本文件的每一条都注明它是从哪一条记录沉下来的。

## 取数

### 走 2.4G 必须是管理员：程序清单挡住了症状，原因没查清，示例程序照旧撞上

非管理员进程写这两个 dongle 的厂商 collection 时，Windows 把写**静默吞掉**：`CreateFile`
拿得到读写句柄、`HidD_SetFeature` 返回 TRUE、`WriteFile` 也成功，**读还全程正常**，没有任何
一层报错。于是那一行说的是「读超时（3000ms 内没有回包）」或者「dongle 连着 10 次都报未就绪」
——**两句都在把用户指向设备那一头**（没插？没配对？睡着了？），而真正的原因在主机这一侧。

2026-09-10 实测：同一个二进制、同一份配置、同一分钟内，非提权读超时，提权首读就拿到
`94% / 4076 mV`。中间为此查了一个多小时的硬件方向。`docs/protocol.md` 第 3 节记着，这个签名在
本项目里出现过两次（另一次是帧缺校验和被设备丢弃），两次都让人往帧格式和硬件上想。

**`juicebar.exe` 从 resident-tray 票 04 起带着要求管理员权限的程序清单**（`build.rs`）：手动启动就
弹 UAC，拒绝就起不来——那是一句明白话，不再是"读超时"。当初列的三个方向（说清要管理员 / 零回包时
提一句 / 程序自己在运行中提权）之外走的是第四条：让 Windows 在启动时就要权限（resident-tray spec
「成品形态」；运行中自己提权那一条被否，理由在那份 spec 的 Further Notes）。剩下的：

- **为什么非提权不可，仍没查清**（resident-tray spec 的 Out of Scope）。清单只是让它不再挡路。
- **诊断用的示例程序不带清单**（`scan`、`probe`、`caps`，只嵌进 bin，见 `build.rs`）：从没提权的终端
  里跑，照旧是那个"读超时"的签名。做协议逆向时要开管理员终端。
- **每次手动启动都弹 UAC**，框里写"未知发布者"（没有代码签名，spec 的 Out of Scope）。开机自启走
  计划任务、开机不弹，归 resident-tray 票 13。
- **过渡期的 `status` 与 `config-refresh` 跟着提权**：从没提权的终端里跑，UAC 之后那个进程借不到原来
  的终端，字没处印；要在管理员终端里跑（parking lot Q160，票 14 收掉这两条子命令时一起消失）。

### 键盘走 2.4G 读不到，而且这条路**可能从来没有真正工作过**

`VGN Neon75` 读不出来：`MI_02` 的就绪位恒为 0，缓冲区停在空闲态常量 `00 64 00 00 01 01 01`。
**同一时刻 HUB 能正常显示 100%**，所以设备、dongle、电池都是好的。

排掉的：**不是权限**（同机鼠标提权后每次都读得到）、**不是键盘睡眠**（睡眠不会让 HUB 卡在
读取页，且键盘醒着时同样失败）、**不是缺初始化**（`F6 0A` 提权试过无效）、**不是时机**
（紧接在 HUB 成功读出之后关掉它立刻连发 100 次 `F7`，就绪位一次都没翻）。

**⚠ 一条排除项撤回**：原先这里写着"不是 dongle 状态（整机重启后不变）"。事后查
`LastBootUpTime` 才发现这台机器当时已连续运行 9 天——那次"重启"是重启 HUB，不是重启机器。
**dongle 从 09-09 那次实测起就没有断过电**，所以"整块 feature 区停在 09-09 的残留上"这条
仍未排除，而它一旦成立，很多推断要跟着重算。断电一次（重启或拔插 dongle）就能分辨。

**要紧的是它比"今天坏了"更严重**：`docs/protocol.md` 第 2 节那条 2026-09-09 的"实测通过"
现在已标为存疑——最可能的解释是当时读到的是 **HUB 刚放进缓冲区的应答**，而不是我们请求换来
的。若如此，这条驱动从来没有真正工作过，只是在一个被 HUB 预热过的缓冲区上看起来能用。

下一步是 USB 抓包（见 `docs/protocol.md` 第 7 节）。**在那之前不要把这条路当成已验证的能力，
也不要因为"曾经能读"就去找回归原因——它可能压根没有过那个"曾经"。**

**在它修好之前，键盘那一行的唯一出路是 BLE 兜底**——Windows 缓存里有它的百分比，只是要用户
自己把 MAC 抄进配置（身份表里没有 BLE 身份，`config-refresh` 补不出来，parking lot Q57）。

### 键盘的充电态永久不显示

驱动交 `charging: None`，`status` 那一格整个不印。原因是 `[9]` 这一位至今没抓到过非零值
（实测期间电池一直满电），`docs/protocol.md` 第 7 节仍把它挂在待实测清单上。硬编一个 `false`
交出去，下游就再也分不清"确实没充电"和"我不知道"。要真显示，得先让键盘电量掉下来复测。
（parking lot Q8）

### 残留帧有一种挡不住

键盘 `0xF7` 的回包既没有 cmd 回显、也没有校验和。就绪标志（`[0] == 1` 才采信）挡住了实测抓到
的那种残留帧，但**残留帧的 `[0]` 恰好是 `0x01` 时，它与一份真应答在字节上不可区分**——协议本身
没留下任何能否决它的字节。现在只能靠"每次取数都紧接着自己发的那条命令读"和"检测到厂商上位机
在跑就暂停 HID"来降低概率。（parking lot Q9）

### 键盘有线本体 `3151:502F` 至今没实测过

要把机身的模式开关拨到有线档才枚举得出来，仅插线不算。身份表 `KNOWN_DEVICES` 里那一条的
`report_id = 0` 是照它的 Dongle24G 抄的。它写下去不会造成错配置（草稿里是注释掉的占位，
`config-refresh` 只在本机真枚举得到时才填成真块），但那一条身份没有证据。
（parking lot Q47；`docs/protocol.md` 第 7 节）

### 键盘的重试上界是个猜的够用值，而定案的人还不存在

`READY_ATTEMPTS = 10`（约 900 ms）。实测键盘闲置后 dongle 会连发 6 次都答未就绪、第 7 次才转
就绪，所以这个数够用；但**该由谁付这笔代价不是驱动能单独决定的**——键盘在 Dongle24G 上多阻塞
一秒，就是 Ble 那条兜底晚一秒才被试。定案的人是常驻轮询那一步（spec 第 7/8 步），它还不存在。

到那一步若要把上界提到 30 次（近 3 秒），**得先把驱动里那个硬编的 `thread::sleep` 做成可注入
的**，否则 `refuses_to_read_a_battery_out_of_a_frame_that_is_never_ready` 那条用例要跟着睡 3 秒
——spec 设 Clock 接缝正是为了"测试不需要 sleep"。另一个更省的旋钮：照 HUB 的 `getDongleData()`
在**首发之前**也补一个 `sleep(100)`。
（parking lot Q10，第 1 趟 `/settle` 决定"维持 10 次，等常驻轮询"）

## 呈现

### 边充电边查表的 Derived Level 会高报，而表中段这一种从没被观测过

`auto` 在 3050–4110 mV 之间走 Derived Level，而那张表是一张**静置电压**表 —— 这一点仓库自己
知道：`docs/protocol.md` 第 6 节记着「电压同步升高也符合物理预期（充电电压高于静置电压）」。
充电器把端电压顶高，查出来的百分比就**高于电池真实的荷电状态**，而那一行只标着「Derived Level」
——那个词说的是算法，不是"它的输入被顶高了"这件事。

`docs/adr/0002` 的缓解**只覆盖表顶以上**（`> 4110 mV` 改用固件自报值，外加充电中 clamp 成 99），
这一段够不着。

**这个高报本身仍然没被观测过**，但"表中段从没被观测过"这句话已经不成立了，2026-09-10 起有了
第一个样本：**4076 mV → Derived Level 94%，且同一时刻 HUB 显示的也是 94%**（鼠标，**未充电**）。
在此之前仓库里的实测电压是 4154 / 4155 / 4158 / 4190 / 4235 mV，全在表顶以上
（3050 / 4110 / 4350 是表界与值域校验，不是读数）。

**这个样本证明了什么、没证明什么，要分清**：

- **证明了**：`voltageToLevel` 的实现在表中段与 HUB 的输出**逐点一致**。这是第一次在表顶以下
  校对上，此前那段代码谁也没验过。
- **没证明**：查表准不准。**HUB 不是真值** —— 那张表本来就是从 HUB 逆出来的，两边用同一个算法，
  对上是应该的，对不上才说明我们抄错了。要判断查表离真实荷电状态有多远，得有一个独立的真值
  来源（放电到关机计时、或者外接负载测容量）。
- **与这一条缺口无关**：那一次取数是**未充电**的。这条缺口说的是"插着线时端电压被顶高、查出来的
  百分比偏高"，它要的样本是**表中段 + 插着线**，仍然没有。
（parking lot Q99 同一趟发现；分类上它是产品缺口而不是执行岔路，所以落在这里而不是 parking lot）


### 设备答坏帧时，那一行最多沉默一天

读取异常撞上"手上有上次已知值"这一支时，那一行不说设备正在回坏帧，只显示历史值。这是有意的，
理由与代价见 `docs/adr/0004`；缺口是它需要一个错误分类才补得上。

### 用户故事 17 是空的：手动切换 Primary 按不到那个按钮

机制齐了——`config::pin_primary` 格式保留地改 `config.toml` 里那一格，八条用例守着。但**触发它
的托盘菜单在 spec 的 Out of Scope 里**，本趟队列没有任何一张票造出它，落盘那一步（`fs::write`）
也没写。于是 `config.example.toml` 第 16–18 行「在托盘菜单里切换 Primary Device 时，新选择会
写回这里」那句话是**半真的**：说的是这一项的设计，不是这个二进制今天做得到什么。
（parking lot Q51）

### 菜单里的"自动（电量最低）"这一项回写不了

`pin_primary` 只收一个 Device id，不支持把 `primary` 设回 `"lowest"`。菜单大概会有这一项，
但它的形状（一个路径？一个 `&mut DocumentMut`？一个带去抖的写入器？）要等托盘那一步才知道。
（parking lot Q52）

## 配置

### 进程名写成不带扩展名就认不出来

暂停判定拿配置里的进程名比本机在跑的进程，比的是路径末段 + ASCII 大小写不敏感，**不补 `.exe`**。
所以 `"VGN VHUB"` 匹配不上实测的 `VGN VHUB.exe`。这一维认不出来的症状是**暂停永远不触发，
和"上位机没在跑"长得一模一样**，属于最难查的那一类。缺省名单里是实测过的完整名字，
所以代价只落在手写名单的人身上。（parking lot Q33）

### 首次运行一台设备都没插，会走进一个死角

`config-refresh` 只往已有的 `[[device]]` 里补空着的块，**不新增 `[[device]]`**（那样会跟"用户
故意删掉一台设备"打架，程序分不出这两种情形）。于是首次运行时一台设备都没插 → 草稿里零个
Device → 插好之后跑 refresh 只会说"没有需要补的空缺"。现在的出路写在草稿里了：把这个文件
删掉再跑一次（那里面没有任何用户写过的东西）。（parking lot Q49）
