# 托盘菜单用普通的原生菜单项：设计稿迁就它，菜单的内容由设计稿导出的基准锁住

设计稿 `.scratch/tray-design/icon-review.html` 用网页画了右键菜单。图标那一层已经做到与设计稿
逐像素对得上（ADR-0005），菜单做不到：README 定的是"原生菜单，零 GUI 框架"，spec 不做自绘弹出
面板，菜单的字和框都由 Windows 画。**决定用普通的原生菜单项（不 owner-draw），把设计稿改到普通项
画得出的样子。**"照设计稿"对菜单说的是它的**内容**：结构、每一项的文字、勾或圆点、右列、是否
变灰、有没有子菜单、预览小图按什么参数画。这些由设计稿导出的菜单基准锁住，内核的菜单模型逐项
比对；外观（字体、行高、高亮、边框）归 Windows。**菜单的深浅跟任务栏走**，靠 uxtheme 里未公开的
函数强制深色或浅色。

普通菜单项能画什么、画不出什么，查证在 `docs/research/native-menu-research.md`。其中有几条
只是推断（右列怎么贴右对齐、圆点和预览小图能不能并排、宽预览会不会把菜单撑坏、强制深色下预览的
透明度），要先写个原型在实机上验证，验证完才改设计稿。

## Considered Options

**全部 owner-draw**：两行的设备行、小灰字标题、变暗的行都画得出。被否是因为系统菜单的外观
（浅色、深色、选中、分隔线、子菜单箭头）要自己一层层重画，深色那几块的主题部件本身是未公开的；
系统会在自绘之后再补画一遍子菜单箭头，得挡掉；Win11 的圆角要自己补，助记键要自己处理。这些全落在
没有自动测试的 Win32 外壳里。字照样由 Windows 光栅化，所以自绘也换不来逐像素。

**只自绘设备行和标题，其余用普通项**：设计稿的样子保得最多。被否是因为同一张菜单里混着两种画法，
而且只要有一项是自绘的，Win11 浅色下的圆角就会丢。

**菜单深浅跟"应用模式"**（交给系统，`AllowDark`）：被否。任务栏跟的是"Windows 模式"，两者可以
不一样；深色任务栏加浅色应用时，菜单是浅的，按深色任务栏画出来的预览放在浅底上，就不再是它在托盘
上的样子，而预览要回答的正是这件事。**不做深色**被否，理由相同，而且要删掉设计稿里深色菜单那一版。

## Consequences

- 设计稿里普通项画不出的三样改掉：
  - 两行的设备行并成一行三段：名字；来源和多久前，读不到时换成短原因（`CONTEXT.md`「短原因」）；
    右列写电量，或者图标状态的名字。完整原因留给悬停提示和日志。
  - "托盘上画哪一台"不再是小灰字标题，改成一个子菜单，右边写当前的选择，写法与"图标样式"的第二层
    相同。
  - 变暗的行用变灰的菜单项表达。变灰的项点不了，而设备行本来就没有点击动作，所以不损失什么。变灰的
    规则跟图标状态走：Stale、暂停、取数失败、Unknown、无已知值。
- **设备行与告警行的措辞归代码**（取数那一层与托盘内核），不归设计稿：那批措辞背后有
  `honest-status-line` 一系列的决定和编码标准，设计稿里的只是示意，所以设备行在基准里只占位。
- 预览小图固定画 57（满电那一组画 100），尺寸按托盘的真实尺寸，调色跟菜单实际的深浅。
- **未公开接口是一笔债**：`SetPreferredAppMode`（uxtheme 序号 135）与 `FlushMenuThemes`（136）
  微软可以在任何一次更新里改掉。只在认得的 Windows 版本上启用（照 Notepad++ 的白名单做法），认不得
  的版本退回浅色菜单。
- 位图交给 Windows 那一步（预乘透明度的 BGRA、行序）做成纯函数加用例：渲染器画对了，像素仍可能在
  这一步被弄错，而 Win32 外壳不做自动测试。手工验收时，真托盘和菜单的截图要与设计稿并排比。
- 翻案面：改成 owner-draw，要重做外壳里的菜单绘制，也要把设计稿这一轮的改动退回去。菜单基准的格式
  不受影响，它只描述内容。
