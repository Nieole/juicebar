# 电量数值的来源，以及不可信值一律当作 Unknown

厂商上位机 VGN HUB 有两处逻辑我们**故意不照抄**。写下来是因为任何对着 `app.asar` 核对实现的人
都会以为这是 bug 并"修回去"。

## 一、表顶改用固件自报值

HUB 的做法是"只要 voltage > 0 就用电压查表覆盖固件自报的 level"，而查表在表顶是硬 clamp：
`if (voltage > 4110) return charging ? 99 : 100`。

一次受控充电前后的实测：电压 4155 → 4190 mV、固件 level 95 → 100，而**查表两次都给 100**。
电池确实增加了电量，固件跟上了，查表没有。因此 juicebar 在电压越过表顶（> 4110 mV）时改用
**Reported Level**，其余区间仍用 **Derived Level**——只在已知查表失效的区间偏离 HUB。

不全盘改用固件值，是因为 HUB 特意绕开它很可能是踩过某些型号的坑，而我们只有一台设备的证据，
不足以推翻它。故保留每个 Device 一个 `level_source` 开关，可整台切回一律用固件值。

## 二、`level == 0` 当作 Unknown，绝不显示 100

HUB 原文是 `battery.level = result[1] == 0 ? 100 : result[1]`，把 0 映射成满电。照抄的后果是
键盘电量真读到 0 时托盘显示 100%——不崩、不报警、每次看都合情合理，而且偏偏发生在最该提醒充电
的时刻。这与本工具存在的全部意义直接冲突。

响应里 `[0]` 已经是独立的就绪标志（HUB 自己在 `[0] == 0` 时会重发），所以 `[1]` 上那条
`0 → 100` 更像是"字段没填好"的兜底。juicebar 一律当作 **Unknown**：保留上次已知值并标灰，
在菜单里说明原因，唯独不显示 100。

## 三、不做 HUB 那套平滑

HUB 的 `calculationBattery` 名为平滑，实为变化率限幅 + 惰性保持——变化落在合理区间内时直接返回
**上一次的值**而不更新。这会让显示值显著滞后于真实下降，与"尽早知道该充电"背道而驰。
juicebar 每次读到什么显示什么。
