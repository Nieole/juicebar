# 设备答坏帧而手上有历史值时，取有界的沉默，不取错误分类

一条 Endpoint 上回来的帧整体不可采信时（读取异常：校验和不对、字段落在物理不可能的值域外），
如果状态文件里还有这台设备的上次已知值，那一行**只显示历史值加"已陈旧，上次已知值"，
不说"设备正在回坏帧"**。备选方案是给取数失败分个类型、让这一支破例把原因印出来；最终选择
**保持沉默**，因为那个分类要穿过每一个驱动的错误路径，而这段沉默是有界的。

## Considered Options

**破沉默**要一个能被 `read_or_last_known` 问的分类（"这一次取数是读到了坏帧，还是压根没读到"）。
靠字符串嗅探是不行的——那条路在 Primary 的暂停判定上已经被否过一次。真做就是一个枚举穿过
每个驱动的错误路径，而"外层那句话该怎么说"这件事**已经被 `lost_reason` 已有的三条分支免费
解决了**（试过了都失败 / 一条都不在场 / 一条都没配），这个枚举买不到别的东西。

**保持沉默**的代价看着比实际大，因为读取异常的头号成因是**厂商上位机在抢同一块共享缓冲区**，
而那一维已经在同一行末尾说话了（"已暂停（VGN VHUB.exe 正在运行）"）。剩下的成因（固件变了、
协议对不上）罕见。

## Consequences

- **沉默最多持续到 `very_stale_after`**（缺省一天）。历史值过期后在 `LastKnown::reading_for`
  那一步就被丢掉，于是那一次取数的真原因照旧印出来。这个失败模式会自己转成可见，不需要人去查。
- 因此这不是"错误被咽掉了"，是"**一天之内先给你一个旧数字，一天之后告诉你出了什么事**"。
  下一个读到这段代码、奇怪为什么一台正在回坏帧的设备安安静静显示旧数字的人，看的就是这一条。
- 哪天真要破这个沉默，代价是那个分类枚举，翻案面是每个驱动的错误路径加 `read_or_last_known`
  一处分支。

## 已被 menu-as-designed 推翻（2026-09-14）

**这份决定已被推翻**，推翻它的是 `menu-as-designed`：`.scratch/menu-as-designed/spec.md`「设备行」
一节，与它的票 04（`.scratch/menu-as-designed/issues/04-short-reason.md`）。上面的原文照旧留着：它说清了
当初为什么沉默，下一个想把分类拆掉的人该先读它。

推翻的是两处：

- **错误分类**。取数失败现在带着它是哪一种来路（`readout::FailureCause`：失联、读取异常、配置里一条
  Endpoint 都没有）。答了坏帧的那一步由驱动与 Transport 包成 `sources::BadFrame`，取数那一层按类型
  认它。"靠字符串嗅探是不行的"那一句仍然成立，这回走的不是那条路。
- **菜单行上的沉默**。菜单那一行在这一次取数没拿到读数时写一句短原因，**手上有上次已知值、右列照样
  写着它时也写**。一台正在回坏帧的设备，菜单上那一行会说读取异常，而不是只显示一个旧数字。命令行
  `status` 那一行与悬停提示不在其内，它们照旧只标"已陈旧，上次已知值"，那段沉默在它们身上仍以
  `very_stale_after` 为界。

**为什么**：菜单的短原因要让用户知道该插线、配对、改配置，还是去关上位机，而失联与读取异常要他做的
事不一样。原文说这个枚举"买不到别的东西"，那时外层只有一句完整原因，`lost_reason`（现名
`failure_reason`）的三条分支够它分说，每条 Endpoint 自己的错误跟在后面。短原因不能带那些错误，
一行菜单放不下（parking lot Q152），只能按来路说，而那三条分支分不出超时与读取异常。

**接受了的代价**：分类穿过了驱动的错误路径。今天的形状是两个驱动在解析回包那一步外面包一层
`BadFrame`，两个 HID Transport 在回包空着或 Report ID 不对时包一层；没包的一律算失联。所以**加一个
驱动、或者在解析那一步之外加一道校验，要记得包它**：漏了不会红，只会让那一种坏帧在菜单上被说成
失联（parking lot Q230）。
