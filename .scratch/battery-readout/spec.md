# 电量取数链路：协议驱动、Device 模型与配置

Status: resolved

对应实现顺序的第 4、5 步。术语一律按 `CONTEXT.md`（Device / Endpoint / Reading /
Reported Level / Derived Level / Stale / Unknown / Primary Device）。相关决策见
`docs/adr/0001`（有线是一等 Endpoint）、`0002`（电量数值来源与不可信值）、
`0003`（回写 config.toml）。协议细节见 `docs/protocol.md`。

## Problem Statement

现在这个工具只能靠 `scan` 和 `probe` 手工敲命令看电量——要记住一长串十六进制、要自己算校验和、
要自己按下标数字节。协议本身已经跑通了，但没有任何东西把它变成"看一眼就知道该不该充电"。

而且两台设备的取数路径差异很大：鼠标插线后会切到另一个 USB 设备、原来的 2.4G 通道直接超时；
键盘插线则什么都不变。蓝牙那条读到的是 Windows 缓存，可能是几天前的。这些差异如果不被统一处理，
托盘上就会出现"明明在充电却显示离线"这类比没有工具更糟的误报。

## Solution

把"一个物理设备当前电量是多少、这个数可不可信"这件事收敛成一条可复用的链路：配置里登记哪些
Device、每个 Device 有哪几条 Endpoint；程序按固定优先级依次尝试取数，产出带来源和时间戳的
Reading；对拿不准的值一律诚实标注而不是猜。

这一步不做托盘，交付一个能在命令行看到全部 Device 当前状态的子命令作为收口——托盘之后接上去
就行。

## User Stories

1. 作为用户，我想让程序自己算校验和、自己拼帧，这样我不必记住 `F7 00 00 00 00 00 00 08` 这种东西
2. 作为用户，我想一条命令看到所有设备的当前电量，这样不必对每台设备各敲一次 `probe`
3. 作为用户，我想在鼠标插着线充电时也能看到它的电量百分比，这样我知道还要等多久
4. 作为用户，我想在鼠标插线时不被显示成"离线"，因为它明明就在我手上用着
5. 作为用户，我想在键盘插线充电时电量照常显示，这样充电不会让我失去可见性
6. 作为用户，我想知道某个读数是刚问出来的还是 Windows 攒了几天的缓存，这样我不会在关键时刻被假的安全感骗到
7. 作为用户，我想在设备失联时看到它上次是多少电，这样我对"收进抽屉那会儿还剩多少"有概念
8. 作为用户，我想让那个历史值在足够旧之后自动消失，这样它不会伪装成现状
9. 作为用户，我想在重启程序后仍能看到上次已知值，这样重启不等于失忆
10. 作为用户，我想让电量真的读到 0 时看到的是"读不出来"而不是"满电"，这样最危险的时刻不会被粉饰
11. 作为用户，我想让读数在明显不合理时显示成异常而不是显示一个荒谬的数字，这样我知道该修工具了
12. 作为用户，我想在刚充满电时看到 100% 而不是 95%，这样数字和我的直觉一致
13. 作为用户，我想能整台切回用固件自报的电量，这样万一某个型号的电压表不准我有退路
14. 作为用户，我想让托盘默认盯住当前电量最低的那台设备，这样我不用手动切换就能看见风险
15. 作为用户，我不想让一个几天前的蓝牙缓存值抢走"最低"的位置，这样"最低"是有意义的
16. 作为用户，我想在菜单里手动钉住某台设备，这样我可以只关心我在意的那个
17. 作为用户，我想让这个手动选择在重启后还在，这样我不必每次开机重选
18. 作为用户，我想让程序改配置时不要洗掉我写的注释，因为那些注释是我理解这份配置的唯一依据
19. 作为用户，我想让程序绝不覆盖我手改过的值，这样我为绕开某个坑做的修改不会被默默改回去
20. 作为用户，我想在首次运行时拿到一份能直接用的配置草稿，这样我不必从零手写
21. 作为用户，我想让草稿明确写出"这一块现在扫不到、你插线后跑某某命令补全"，这样我不会不知道自己缺了什么
22. 作为用户，我想在插好线之后用一条命令补全配置，这样我不必手抄 VID/PID
23. 作为用户，我想让 2.4G 轮询省着来，这样这个工具本身不会成为耗电的原因
24. 作为用户，我想让有线和蓝牙轮询快一些，因为它们不耗设备的电
25. 作为用户，我想在厂商上位机运行时自动暂停 HID 轮询，这样两个程序不会互相把对方的应答冲掉
26. 作为用户，我想在暂停期间蓝牙照常更新，因为它根本不参与那个竞争
27. 作为用户，我想在暂停期间看到"暂停中"而不是"失联"，这样我不会以为设备出问题了
28. 作为用户，我想给键盘和鼠标设不同的低电阈值，因为它们的续航差得远
29. 作为用户，我想在不关心时直接用一个全局低电阈值，这样常见情况下配置很短
30. 作为用户，我想在拔线的那一刻立刻看到数据源切回 2.4G，而不是空窗一个轮询周期
31. 作为接入新设备的人，我想加一个协议家族只需要加一个模块，这样不必改动既有代码
32. 作为接入新设备的人，我想在配置里绑定 VID/PID 到驱动，这样加设备不需要重新编译
33. 作为接入新设备的人，我想让同一个驱动覆盖该家族的有线和 2.4G 两种 Endpoint，这样不必写两份几乎相同的代码
34. 作为维护者，我想用真实抓到的字节做测试夹具，这样测试证明的是"对着真硬件的行为"而不是"对着我的想象"
35. 作为维护者，我想在不接任何硬件的情况下跑全部测试，这样 CI 和别人的机器上也能跑
36. 作为维护者，我想让"拔线后降级"这类场景可测，这样这条最容易写错的路径有回归保护
37. 作为维护者，我想让陈旧判定可测且不依赖真实时间流逝，这样测试不需要 sleep
38. 作为维护者，我想让协议解析的错误信息说清是哪一步失败的，这样厂商换固件时能快速定位
39. 作为以后有两台同型号设备的用户，我想靠无线地址把它们分开，这样它们不会在界面上打架
40. 作为只有一台的用户，我不想被强制填写无线地址，这样常见情况配置依然简单

## Implementation Decisions

### 模块划分

- `src/sources/` 下每个协议家族一个模块：`vgn_mouse`、`vgn_keyboard`。两者实现同一个驱动
  trait，**一个驱动覆盖该家族的所有 Endpoint 种类**，内部按 Endpoint 种类分支（键盘的
  `Dongle24G` 与 `Wired` 命令不同；鼠标两者相同，分支自然退化）。
- Device 模型、Endpoint 合成、陈旧判定、Primary 选择集中在一处，与驱动解耦：它只消费 Reading，
  不知道协议。
- 配置读写单独一处，负责解析、自举草稿生成、以及**格式保留的回写**。
- `Ble` Endpoint 不经过驱动——它走 `bluetooth.rs` 已有的 Windows 属性读取。配置里的 `driver`
  字段只作用于 HID Endpoint。

### 三个接缝

1. **Transport**：包住 HID 的一次字节往返，`exchange(&[u8]) -> Result<Vec<u8>>`。具体实现自己
   知道该走 output+input 还是 feature、用哪个 report id、超时多少（鼠标 3000 ms，见
   `docs/protocol.md`）。驱动只面对这一个方法，两种协议的 I/O 差异被吸收在实现里。
2. **Clock**：供陈旧判定使用，避免测试依赖真实时间流逝。
3. **枚举**：回答"当前哪些 Endpoint 在场"。逻辑很薄，单独抽出来是为了能测"拔线 → `Wired` 从
   枚举里消失 → 同周期降级到 `Dongle24G`"这条路径——那是实测确认过、也最容易写错的行为。

### 取数流程

- 优先级 **`Wired` > `Dongle24G` > `Ble`**，依次尝试，遇第一个成功即停。
- 靠前的 Endpoint 失败时**在同一个轮询周期内立刻降级**，不等下一轮。拔线时 `Wired` 直接从枚举
  里消失（瞬时失败而非超时），降级代价接近零。
- 全部失败才算失联。
- 鼠标只发 `cmd 4`，**不发 `cmd 3`**：`cmd 4` 是否回有效帧本身就蕴含在线与否，且 `cmd 3` 的
  `[5]` 语义存疑（实测更像充电标志而非在线标志）。

### 电量数值

- `level_source` 是**每 Device** 的项，没有全局默认（缺省视为 `"auto"`）：
  - `"auto"`：电压 > 4110 mV 时用 **Reported Level**，其余区间用 **Derived Level**
  - `"reported"`：一律用 Reported Level
- 键盘 `level == 0` 一律当作 **Unknown**，绝不映射成 100（HUB 会，我们有意不照抄）。
- 合理性校验：level ∈ 0..=100、voltage ∈ 3050..=4350 mV、cmd 回显与请求一致、校验和对得上。
  任一不过按"读取异常"处理，不显示数字。
- Derived Level 的查表与插值照 `docs/protocol.md` 记录的 `voltageToLevel` 实现，含 `> 4110`
  clamp（充电中取 99）和 `level == 0 || level == 15` 时加一的怪癖。
- **不做** HUB 那套变化率限幅/惰性保持。

### 新鲜度与持久化

- HID Endpoint 的陈旧阈值 = **3 × 该 Endpoint 的轮询间隔**，自动推导，不设配置项。
- `Ble` 用配置里的 `stale_after` / `very_stale_after`。
- 最近一次成功的 Reading 持久化到 `%APPDATA%\juicebar\` 下的状态文件，重启后可用；超过
  `very_stale_after` 即丢弃。该状态文件只放运行时缓存，不放用户可见的配置选择。

### Primary Device

- `primary = "lowest"` 时，只有**新鲜且可信**的 Reading 参与比较；陈旧、Unknown、失联的都不参与，
  全都不可信时保持上次的选择。正在充电的 Device 照常参与。
- 菜单里的手动选择**回写 `config.toml`**（用格式保留的 TOML 编辑，见 ADR-0003）。

### 配置

- 新增 `[device.wired]` 块、`poll_interval_wired`、每 Device 的 `level_source`、可选的
  per-device `low_battery`、可选的 `address`（同型号多台时区分，取自协议能问出的无线地址）。
- 自举草稿里为扫不到的 `[device.wired]` 留**注释掉的占位**并写明补全办法。
- 新增补全命令（拟名 `config-refresh`）：只填空着的 Endpoint 块。
- **回写边界**：只补空缺和程序自己管的字段（`primary`、`config-refresh` 填充的块），
  **绝不修改用户已经写过的值**；扫描结果与用户所写不一致时只在命令行提醒。

### 暂停

- 检测到 `vendor_hub_processes` 里的进程在跑时，暂停 `Wired` 和 `Dongle24G`，`Ble` 照常。
- 暂停状态要与失联区分开，不能显示成失联。

### 收口

- 新增一个打印全部 Device 当前状态的子命令（拟名 `status`），一行一个 Device，含名字、电量、
  状态原因、来源 Endpoint、多久前——即托盘菜单将来要显示的同一组信息。

### 依赖

- 新增 `toml_edit`（格式保留的 TOML 编辑）。按仓库惯例在 `Cargo.toml` 里写明收它的理由。

## Testing Decisions

**什么算好测试**：只测外部行为——"给这样的输入，产出什么 Reading / 选中哪个 Device / 往设备发了
哪些字节"。不测私有函数、不断言内部调用次数、不为了可测性把实现细节暴露出来。三个接缝之外的一切
都写成纯函数，用普通的输入输出断言即可。

**测试夹具用今晚实测抓到的真实字节**，它们经过 CRC 验算、来自真硬件，比手编的样本可信得多：

```
鼠标 cmd 4 静置满电   08 04 00 00 00 02 64 00 10 5E 00 …  →  level 100, 未充电, 4190 mV
鼠标 cmd 4 静置 95%   08 04 00 00 00 02 5F 00 10 3E 00 …  →  level 95,  未充电, 4158 mV
鼠标 cmd 4 充电中     08 04 00 00 00 02 5F 01 10 8B 00 …  →  level 95,  充电中, 4235 mV
键盘 F7 满电          00 01 64 00 01 01 01 01 00 …        →  level 100, 未充电
键盘 F7 未就绪        00 00 64 00 00 01 01 01 00 …        →  [0]==0，应重试而非采信
```

**要测的模块与场景**：

- **驱动（经假 Transport）**：发出去的帧是否正确（含校验和、命令码按 Endpoint 种类分支、补零
  长度）；上面每条真实回包是否解析成预期的 Reading；CRC 不符、cmd 回显不符、电压越界时是否
  按"读取异常"处理而不是产出数字；键盘 `level == 0` 是否产出 Unknown 而非 100。
  **回归重点**：帧不带校验和时必须被视为构造错误——今晚整条链路失败的根因就在这里。
- **电压查表（纯函数）**：表内插值、表顶 clamp（充电中 99 / 否则 100）、
  `level == 0 || level == 15` 加一的怪癖、表底边界。
- **level 来源选择（纯函数）**：`"auto"` 在 4155 mV 时取 Reported Level（95）而非 Derived
  Level（100）；`"reported"` 一律取固件值。
- **Endpoint 合成（经假枚举 + 假 Transport）**：优先级顺序；`Wired` 在场时不去打扰
  `Dongle24G`；`Wired` 从枚举中消失后同周期降级；全部失败才算失联；暂停态与失联态可区分。
- **陈旧判定（经假 Clock）**：HID 按 3× 轮询间隔变陈旧；`Ble` 按配置阈值；持久化读数超过
  `very_stale_after` 被丢弃。
- **Primary 选择（纯函数）**：陈旧/Unknown/失联不参与 lowest；充电中的参与；全都不可信时保持
  上次选择。
- **配置回写**：注释在回写后仍然存在；用户手写过的值不被修改；只有空缺块和程序管理的字段被填。

**先例**：仓库目前**零测试**，这份 spec 建立的就是先例。因此测试的组织方式（放哪、怎么命名、
夹具怎么共享）需要在第一个模块里定好，后续照抄。

## Out of Scope

- 托盘图标渲染与菜单。图标设计按共识必须先做成本地可交互网页给用户审（3–4 个方向 × 四状态 ×
  四尺寸，带浅/深底色切换和 1:1 对照条），审过才允许写渲染代码。**"完全没有已知值时图标画什么"
  这个问题留在那一步决定，不在本 spec 内。**
- 单实例（互斥体）、开机自启（注册表 Run 键，默认不开）、日志——属于第 7、8 步。
- 键盘 `charging` 位的验证：实测期间电池一直满电，没抓到 `charging != 0` 的样本。键盘暂不显示
  充电态，不阻塞本 spec。
- 键盘有线本体 `502F` 的实测：需要把机身模式开关拨到有线档才枚举，尚未验证。配置里先留注释占位。
- 明确不做：寄生 HUB 的 localStorage、BLE GATT 主动读取、自绘弹出面板、剩余时间估算、信号强度、
  DPI/回报率、声明式协议配置 TOML、脚本插件、跨操作系统。

## Further Notes

- 今晚整条键盘链路失败的根因是**发出去的帧缺一个校验字节**，而 `HidD_SetFeature` 照样返回成功、
  `HidD_GetFeature` 照样交回缓冲区里的陈旧残留且不报错。教训写在 `docs/protocol.md` 里：
  **API 返回成功只代表驱动收下了，不代表设备认这一帧。**这直接影响错误处理的写法——驱动不能把
  "调用没报错"当作"读到了"，必须校验回包内容本身。
- 键盘 dongle 的 feature 报文是一块**保存最近一次应答的共享缓冲区**。这是暂停策略的机械依据，
  也意味着驱动必须校验回包的 cmd 回显，否则可能把上一条命令的应答当成本次结果。
- 两台设备插线行为不同，判定逻辑不能通吃：鼠标插线即切有线传数据（`1005` 枚举、dongle 超时）；
  键盘要拨到有线档才枚举 `502F`，仅插线时数据仍走 2.4G 且 dongle 照常应答。
- 鼠标有线 PID `0x1005` 与 dongle 的 `0x1A05` 只差一个字符，极易写混。
