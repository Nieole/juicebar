# 菜单照设计稿

Status: ready-for-agent

术语一律按 `CONTEXT.md`（Device / Endpoint / 一次取数 / 一轮 / Stale / Unknown / 取数失败 / 暂停 /
上次已知值 / Primary Device / 图标状态 / **短原因** / **告警**，后两个是这一次新收的）。相关决策：
`docs/adr/0005`（图标设置全部开放；图标与设计稿逐像素对上）、**`0006`（菜单用普通原生菜单项，设计稿
迁就它；菜单的内容由设计稿导出的基准锁住；菜单深浅跟任务栏）**、`0003`（格式保留回写）、**`0004`
（坏帧时取有界的沉默——本 spec 推翻了它的两处，见「设备行」）**。设计稿
`.scratch/tray-design/icon-review.html`（2026-09-10 定稿，本 spec 要改它）。原生菜单能画什么的查证：
`docs/research/native-menu-research.md`。

出处是 2026-09-10 到 11 日那次 `/grill-with-docs`，起因是用户问"怎么让这个程序做出来的 UI 严格照设计稿
出效果"。**本 spec 改动 `resident-tray` 的票 06、07、09、11、12**（见 Implementation Decisions 末节），
那几张票里与本 spec 相冲的验收，以本 spec 为准。

## Problem Statement

用户要的是：**托盘做出来的样子，就是审过的设计稿的样子。**图标已经做到了——设计稿导出文本网格，
Rust 的渲染器逐像素去比，对不上就红（`resident-tray` 票 01）。菜单没有，而且差在好几处：

**一、没有从设计稿导出的东西可比。**票 06、07 只写着"照设计稿"，验收靠手工，外加实现的人自己抄进用例
的字符串。实现的人读 HTML 自己理解，抄错了，测试照样是绿的。

**二、设计稿里有普通原生菜单画不出的东西。**设备行是两行（名字下面一行小灰字），"托盘上画哪一台"是
一行小灰字标题——普通菜单项只有一行字，也没有标题这种项。照着做，实现的人只能自己挑一种画法；而
改用自绘（owner-draw），系统菜单的外观要自己一层层重画，全落在没有自动测试的外壳里（ADR-0006）。

**三、设计稿缺好几块。**"登记设备 ›"整个子菜单、菜单顶上的告警、配置里一台 Device 都没有时的那句
说明，设计稿里都没有。这几块实现时只能由实现的人排。

**四、设计稿里的设备行措辞与代码对不上。**设计稿写"来自 Dongle24G，0 秒前"，代码写"来自 Dongle24G
（0 秒前）"；蓝牙那条代码还多"（Windows 缓存，…）"半句；失败那一行两边口吻也不同。而代码那一套措辞
背后有 `honest-status-line` 一系列的决定和编码标准。

**五、"短原因"多短从来没定（parking lot Q152）。**取数失败那一句带着每条 Endpoint 各自的错误，一行
菜单放不下；今天没有一句短的说法。

**六、告警只活一轮（parking lot Q162）。**告警只进日志时没关系，一上菜单就会一闪一闪：打开菜单看不看
得到它，全凭这一轮碰巧是哪台 Device 的取数开的头。

**七、菜单的深浅没有着落。**设计稿画了深色菜单，而 Windows 没有让弹出菜单变深的公开接口。托盘图标跟
"Windows 模式"（任务栏的深浅），菜单交给系统时大概率跟"应用模式"；两者不一样时，按任务栏调色画的
预览放在另一种底色上，就不再是它在托盘上的样子。

**八、最后一段没人守。**位图交给 Windows 的那一步写在外壳的 unsafe 里：托盘图标要不预乘的 BGRA，
菜单里的预览位图要预乘过的。哪一处弄反，托盘上的颜色或边缘就与设计稿不一样，而渲染器的用例全绿。

**九、调研里几条关键能力只是推断。**右列怎么贴右对齐、圆点和预览小图能不能并排、宽预览会不会把菜单
撑坏、带子菜单的项右边显不显示当前值、强制深色下预览的透明度对不对——普通菜单这条路恰好靠它们。

## Solution

1. **普通原生菜单项，设计稿迁就它**（ADR-0006）。顺序是：先写个原型在实机上把那几条推断验证掉 →
   按实机结果改设计稿、补齐缺的几块 → **用户审过** → 菜单那几张票照新的设计稿与基准做。
2. **设计稿导出菜单基准**：一项一行的文本。内核的菜单模型排成同样的文本去比，全部菜单都导；设备行与
   告警行的措辞归代码，基准里只占位。
3. 菜单自上而下：告警 → 设备行 → "托盘上画哪一台 ›" → "图标样式 ›" → "菜单显示 ›" → "登记设备 ›" →
   开机自启 → 打开配置文件 → 退出。
4. **设备行一行三段**：名字；来源和多久前，这一次没拿到读数时换成短原因；右列写电量或图标状态的名字。
   该变灰的行变灰。完整原因在悬停提示与日志里。
5. **告警挂到那件事下一次办成为止**，点一下打开日志。
6. **菜单深浅跟任务栏**，预览小图固定画 57、按托盘的真实尺寸、跟菜单的深浅。
7. **位图交给 Windows 之前的那一步成为纯函数**，有用例守着；其余的最后一段靠一张截图对照的手工清单。

## User Stories

### 菜单与设计稿

1. 作为用户，我想右键菜单的结构、每一项的字、勾和圆点、右边写的值与设计稿一样，这样我审过的设计稿就是
   我拿到的菜单
2. 作为用户，我想设计稿里画的菜单就是 Windows 原生菜单画得出的样子，这样设计稿不会许一个程序兑现不了
   的诺
3. 作为审设计稿的用户，我想设计稿里画着每一块会出现的菜单——包括登记设备、告警、一台 Device 都没有
   ——这样没有哪一块是实现的人自己排的
4. 作为用户，我想设计稿改完先给我审，审过才开始照它实现，这样改过的设计稿不会没人看过就成了基准
5. 作为下一个动菜单的开发者，我想菜单的内容与设计稿导出的基准逐项比对、对不上时差异读得懂，这样我
   知道是菜单模型错了，还是设计稿该改
6. 作为下一个改设计稿的人，我想改完跑一次导出就更新了基准，而不是手改基准文件，这样基准永远是设计稿的
   样子
7. 作为开发者，我想设计稿依赖的每一样原生菜单能力都在实机上验证过，这样改完设计稿，不会到实现时才
   发现画不出

### 设备行

8. 作为用户，我想每台 Device 一行，写着名字、来源和多久前、电量，这样一次看全
9. 作为用户，我想这一次没拿到读数的那一行写一句短原因——失联、读取异常、配置里一条 Endpoint 都没有，
   或者被哪个上位机暂停——这样我知道该插线、配对、改配置，还是去关 HUB
10. 作为用户，我想短原因短到一行放得下，完整原因在悬停提示和日志里，这样菜单不会被一台设备的错误撑得
    很宽
11. 作为用户，我想右列写电量，没有数可写时写图标状态的名字，这样右边那一列一眼扫得完
12. 作为用户，我想图标状态是 Stale、暂停、取数失败、Unknown、无已知值的那几行变灰，这样一个不是此刻
    的数不会被我当成现状
13. 作为用户，我想一台读不到了、而上次已知值是低电的设备那一行不变灰，这样它没电关机时照样显眼
14. 作为用户，我想关掉"写出来源和多久前"之后，有读数的行只写电量，读不到的行照样写短原因，这样关掉
    来源不等于关掉原因
15. 作为用户，我想"在设备列表里标出 Primary Device"开着时 Primary Device 那一行打勾，这样一眼知道
    托盘此刻画的是谁
16. 作为用户，我想设备行、悬停提示与日志说同一件事时用的是同一套说法，这样我不会以为是两件事

### 托盘上画哪一台

17. 作为用户，我想"托盘上画哪一台 ›"右边写着我现在的选择，这样不点开也知道是自动还是钉死了某一台
18. 作为用户，我想点开后是"自动（电量最低）"和每台 Device 的单选，圆点落在我的选择上，这样切换一下
    就行
19. 作为用户，我想一级菜单里设备名不出现两遍，这样我分得清哪一组说的是状态、哪一组是设置

### 告警

20. 作为用户，我想认不出本机在跑哪些进程、读数记不进状态文件、配置文件读不了的时候，菜单最顶上各有
    一行告警，这样这些不属于任何一台设备的事我也知道
21. 作为用户，我想一条告警一直挂着，直到那件事下一次办成，这样不会这次打开菜单看得到、下次就没了
22. 作为用户，我想点一下告警就打开日志、看到完整原因，这样不必自己去配置文件旁边找日志
23. 作为用户，我想配置读不了那条告警，在我改好、程序读好之后自己消失，这样菜单上挂着的就是此刻还没好
    的事

### 图标样式与菜单显示

24. 作为用户，我想"图标样式"第二层每一行右边写着当前值，一级那一行右边不写字，这样与设计稿一致
25. 作为用户，我想最里一层每个选项前面有一张预览，当前选项前面有圆点，缺省选项右边写"默认"，B 电池
    右边写"16、20 像素不显示数字"，这样选之前就知道它长什么样、代价是什么
26. 作为用户，我想预览画的是一个固定的示例电量（"满电 100"那一组画 100），这样预览每次都一样，说的是
    "这个选项长什么样"，而不是"我现在多少电"
27. 作为用户，我想预览按我托盘此刻的真实尺寸画、跟菜单的深浅一致，这样预览就是它在托盘上的样子
28. 作为用户，我想"灰状态"那一组预览把 Stale、暂停、取数失败三张并排，这样一眼看得出三种状态怎么分

### 登记设备与一台都没有

29. 作为用户，我想"登记设备 ›"子菜单的结构与设计稿一样，这样登记这件事也是审过的样子
30. 作为第一次用的用户，我想配置里一台 Device 都没有时，设备行那一块写一句说明，这样我不会对着一个空
    菜单发愣

### 深浅色

31. 作为深色任务栏的用户，我想菜单也是深色的，这样菜单、托盘图标、预览是同一套调色
32. 作为"深色任务栏、浅色应用"的用户，我想菜单跟任务栏而不是跟应用，这样预览放在菜单上就是它在托盘上
    的样子
33. 作为用户，我想切换任务栏深浅之后，下一次打开的菜单跟着换，这样不必重启程序
34. 作为用旧版 Windows 的用户，我想程序认不得我的版本时菜单退回浅色，而不是出错或画花，这样菜单总是
    能用

### 最后一段

35. 作为用户，我想托盘图标和菜单预览的颜色、半透明的边缘与设计稿一致，这样不会有一圈黑边或一片发白
36. 作为开发者，我想"位图交给 Windows 之前"那一步有用例守着，这样渲染器画对了、交接却错了的时候会红
37. 作为开发者，我想手工验收有一张截图对照清单，这样自动测试够不着的那一段也有人看过

## Implementation Decisions

### 画法（ADR-0006）

- **普通原生菜单项，不 owner-draw**。设计稿改到普通项画得出的样子，而不是反过来。
- 右列用普通项自带的那一列。用"制表符那一列"还是"贴右对齐的那个字符"，由原型的实机结果定，定成
  最贴近设计稿的那一种。
- 变灰就是禁用的菜单项。设备行本来没有点击动作，所以变灰什么都不损失。
- 预览是挂在菜单项上的 32 位预乘位图，**不**设"勾与位图共用一格"的那个菜单样式，好让圆点与预览并排
  （原型确认）。

### 菜单自上而下

告警（有才出现）→ 设备行，或者"一台 Device 都没有"的那句说明 → "托盘上画哪一台 ›" → "图标样式 ›" →
"菜单显示 ›" → "登记设备 ›" → "开机自启" → "打开配置文件" → "退出"。分隔线的位置由设计稿定。

### 设备行

- **一行三段**：〔勾〕名字 ｜ 中段 ｜ 右列。
- **中段**：这一次取数拿到了读数 → 来源和多久前（"写出来源和多久前"关着时这一段空着）；这一次没拿到
  读数（取数失败，或者暂停）→ **短原因**，不受那个开关影响——即使手上有上次已知值、右列照样写着它。
- **右列**：手上有数（这一次的读数或上次已知值）→ 电量；没有数 → 这一台的图标状态的名字。
- **变灰**：这一台的图标状态是 Stale、暂停、取数失败、Unknown、无已知值之一。图标状态的优先顺序照旧
  （`CONTEXT.md`），所以一台读不到了、上次已知值低电的设备按低电走，不变灰。
- **勾**：`primary_mark = "both"` 时 Primary Device 那一行打勾（ADR-0005 与设计稿）。
- **措辞归代码，不归设计稿。**
  - 取数那一层交出取数失败属于哪一种来路（`CONTEXT.md`「取数失败」的三种）。短原因按来路各一句，
    暂停那一句点名是哪个上位机。这定了 parking lot Q152：**另写短句**，不拿完整原因截断。
  - 完整原因照旧是今天那一句，悬停提示与日志里用它。短原因与完整原因的措辞各只在一处定，菜单、悬停
    提示、日志共用。
  - 中段其余的措辞（来源怎么说、充电中与陈旧怎么标）沿用代码今天的说法。
  - 设备行在设计稿基准里只占位，确切字符串由内核的用例断言。
- **这推翻了 ADR-0004 的两处**（写 spec 时漏查，由队列发现，用户 2026-09-14 拍板推翻）：
  - 0004 否掉了"给取数失败分类"，这里要分出失联与读取异常；
  - 0004 定的是"设备答坏帧而手上有上次已知值时，只显示历史值、不说原因"，这里即使有上次已知值，
    中段照样写短原因。
  
  推翻了什么、为什么、接受了什么代价，由 `menu-as-designed` 票 04 写进 ADR-0004 那一节。
- 设备行没有点击动作。

### 托盘上画哪一台

- 一个子菜单。右列写**用户的选择**——"自动（电量最低）"或者钉死的那一台的名字——不是这一轮的
  Primary Device（这一轮是谁，看设备行上的勾）。
- 里面是"自动（电量最低）"与每台 Device 的单选，圆点落在用户的选择上。点了之后照 `resident-tray`
  票 06 格式保留地写回配置。

### 告警

- 菜单最顶上，一条告警一行。普通项，不变灰，**点一下打开日志文件**。
- 三种：认不出本机在跑哪些进程、这一轮的读数记不进状态文件、配置文件读不了（沿用上一份读好的）。
- **粘住**：一条告警挂到那件事下一次办成为止——下一次问得出进程、下一次写得进状态文件、下一次读好
  配置——不随一轮来去。这定了 parking lot Q162。每次发生照旧把完整原因写进日志。
- 措辞归代码，设计稿与基准里只占位；告警区的位置与形状进基准。

### 图标样式与菜单显示

- 一级"图标样式 ›"右边不写字。第二层六行，右边写当前值，末尾"恢复默认"（只恢复这六项）。最里一层每个
  选项：当前值前面是圆点，然后是预览、文字，右边写"默认"或者"16、20 像素不显示数字"——照设计稿。
- **预览**：只把这一项换成该选项，其余设置照用户当前的；电量固定 **57**，"满电 100"那一组画 100。每一项
  预览画哪个图标状态照设计稿：画法、字形、满电 → 正常；没有读数时 → 无已知值；充电标记 → 充电中；
  灰状态 → Stale、暂停、取数失败三张并排，间距照设计稿。
- 预览的尺寸是托盘此刻那一档；调色跟菜单实际的深浅——正常情况下就是任务栏的深浅，退回浅色菜单时画
  浅色。
- 几张并排的拼法是渲染那一层的一个纯函数。
- "菜单显示"的两项照 `resident-tray` 票 07。

### 菜单深浅（ADR-0006）

- 跟任务栏的深浅，也就是外壳为托盘图标已经在读的那个值。菜单弹出之前，按它把首选模式设成强制深色或
  强制浅色，再刷新菜单主题（uxtheme 里未公开的那两个函数）。
- **只在认得的 Windows 版本上启用**，照 Notepad++ 的白名单做法，但从 Windows 10 1903 起、全部 Windows 11——1809 只能"允许深色"、菜单跟应用模式，做不到跟任务栏，不认（parking lot Q260，用户 2026-09-14 定）。
  认不得就一个都不调，菜单是系统缺省的浅色，预览随之画浅色。版本判断是一个纯函数。
- 任务栏的深浅变了，下一次弹出的菜单跟着换；预览随之重画（`resident-tray` 票 07 那条"深浅切换时
  重画"）。

### 位图交给 Windows

- 两个纯函数：给托盘图标的字节（不预乘的 BGRA，自顶向下）、给菜单预览的字节（预乘过的 BGRA）。托盘
  图标与预览都走它们，外壳里只剩把字节交给 Windows 的那几行。

### 菜单模型与基准

- 内核的菜单模型描述**内容**：每一项的种类（普通 / 勾选 / 单选 / 子菜单 / 分隔线）、文字、勾或圆点、
  右列、是否变灰、预览参数（设置、图标状态、电量、尺寸、调色、几张并排）、点了收到什么。外壳只把它画
  出来，不做决定。
- 基准是文本：一项一行，子菜单的内容跟在它下面、缩进一格；设备行与告警行的措辞用占位。与图标基准同一套
  规矩：由设计稿导出，文件头写明"别手改：改设计稿，再跑导出"。
- 覆盖面：全部菜单——一级、托盘上画哪一台、图标样式与它的六个子菜单、菜单显示、登记设备。从缺省出发
  只改一项、每个取值各一份；另加有告警、一台 Device 都没有，以及登记设备的几种情形（有未登记的蓝牙
  设备、有认得但没登记的 HID 设备、有可以解除的蓝牙登记、什么都没有）。
- 基准里用的是设计稿里那份罐装配置；用例喂同一份配置，比对失败时打印两份文本的差异。
- 灰状态那一组"三张并排"的预览另导像素基准，格式与图标基准相同。

### 设计稿（要改）

- 照上面各节改：设备行一行三段；已有的措辞照代码今天的说法，还没有的用占位，并注明以代码为准。
  "托盘上画哪一台"改成子菜单；补上告警区、"登记设备 ›"子菜单（结构照 `resident-tray` spec 的"菜单"
  一节）、一台 Device 都没有时的说明；变灰规则；预览固定 57；深色菜单那一版保留。
- 加"导出菜单基准"的入口与导出脚本，照图标基准的做法；外加灰状态并排预览的像素基准。
- **只画到原型验证过画得出的样子**：原型推翻了哪一条推断，设计稿就按实机结果画。
- **用户审过才算完**：ADR-0005 那道"先给用户审、审过才写代码"的门槛，这一次照样。

### 原型（先于设计稿）

- 一个用完就扔的 Win32 小程序，用普通菜单项建出新形状的菜单：一级、托盘上画哪一台、图标样式第二层、
  画法与灰状态两个最里层、告警行、变灰的设备行。浅色、强制深色各一份。
- 它回答调研"查不实的"一节里这条路要靠的那几条：右列怎么贴右对齐；带子菜单的项右列显不显示、挨不挨着
  箭头；圆点与预览位图能不能并排；32 像素的预览与"三张并排"的宽预览把项撑成什么样；变灰的项悬停时是
  什么样子；强制深色下预乘位图的透明度照不照常；强制深浅与刷新菜单主题是不是即时生效；"深色任务栏、
  浅色应用"时强制深色压不压得住。
- 结论与截图补进调研文件（截图放在它旁边）；代码留在一个 `prototype/` 分支上，不进 master。

### 与 `resident-tray` 的关系

- **票 06**：设备行、"托盘上画哪一台"、告警区（认不出进程、记不下读数这两种的粘住与点开日志）、
  一台 Device 都没有时的说明，照本 spec；取数那一层交出来路、短原因；菜单模型与一级、托盘上画哪一台两份
  基准比对。它要等设计稿审完。
- **票 07**：图标样式与菜单显示两份基准比对；预览固定 57、并排的拼法；菜单深浅跟任务栏；位图交给
  Windows 的两个纯函数。
- **票 09**：配置读不了进告警区，粘到下一次读好、点开日志。它要等设计稿审完。
- **票 11、12**："登记设备 ›"与它的基准比对。
- 那几张票怎么改、哪几件不依赖设计稿可以先拆出去跑，由 `/to-tickets` 定。

## Testing Decisions

好的测试只测外部行为，不测私有函数：这个仓库用集成测试，让编译器守着这一条。

**四道缝：三道现成、一道新开**（写 spec 时与用户确认过）。

- **托盘内核**（现成）：
  - 菜单模型排成基准的文本格式，与设计稿导出的全部菜单基准逐份比对；
  - 设备行的确切字符串：短原因的三种来路与暂停各一例，有读数的行在"写出来源"开与关两种下各一例；
  - 变灰规则：五种变灰的图标状态各一例，外加"读不到、上次已知值低电"那一行不变灰；
  - Primary Device 的勾（`primary_mark` 两个取值）；
  - "托盘上画哪一台"的右列与圆点：自动、钉死各一例；
  - 告警：三种各一例，挂着、以及下一次办成之后消失；点告警时内核交出"打开日志"；
  - 一台 Device 都没有。
  
  prior art：菜单与悬停提示那几份用例对确切字符串的断言；罐装的一次取数结果与假时钟。
- **图标渲染**（现成）：几张并排的预览与设计稿导出的像素基准逐像素比对（灰状态三个取值 × 4 个尺寸 ×
  2 种调色）。prior art：图标用例里的"与设计稿比对"，失败时打印两张网格的差异。
- **一次取数**（现成）：取数失败交出它是哪一种来路，三种各一例。prior art：取数那一层现有的用例。
- **外壳交给 Windows 之前的纯函数**（新）：不预乘与预乘两种 BGRA 字节，都要覆盖半透明像素、全透明像素
  与行序；版本白名单的边界（1809 与之前、1903、Windows 11）。
- **不自动测的**：真的弹出菜单、强制深浅真的生效。这一段靠原型的实机结论，外加一张手工验收清单：四档
  缩放 × 深浅两种，真托盘与菜单的截图和设计稿并排比；"深色任务栏、浅色应用"看一次；运行中切一次深浅。
- gate 三条（`fmt --check`、`clippy --all-targets -D warnings`、`test`）全绿。

## Out of Scope

- **owner-draw**，以及菜单的逐像素（ADR-0006）：菜单的字体、行高、高亮、边框归 Windows。
- 系统通知与悬停提示的样子：设计稿里没有，它们由 Windows 画。悬停提示的措辞 `resident-tray` 票 04
  已经定了。
- 高对比度模式：系统会关掉菜单主题，照系统。
- Windows 10 深色菜单的边框颜色：那是 owner-draw 才要处理的事。
- `rt-05` 查出的节奏缺陷（2.4G 反而被问得更勤）：单独一张 needs-triage 的票，修法另定。
- 键盘 2.4G 读得到读不到：另一边在实验，本 spec 不对它下任何断言。
- parking lot Q203、Q204：随票 09、13，照队列的推荐。
