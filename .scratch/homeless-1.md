# 第 1 趟 `/settle` 结算出来的 5 条无主的活

**Status:** 交接文件 —— 给 `/grill-with-docs` 用，磨完就可以删
**Opened:** 2026-09-09
**出处:** `.scratch/parking-lot.md` 的第 1 趟结算索引；这 5 条的正文在 git 的 `75eb3da` 里

## 读这份东西的人要先知道两件事

**一、这一堆做过的思考比一般的想法更少。** `/settle` 的分道是**只贴标签、不做决定**，所以这里
每一条都还是一袋观察，不是一条磨过的线。**预期它在 grill 里缩水**——有些想清楚了其实是记录，
或者是上游已经答过的问题。

**二、它们的共同点是：当时不做的理由都是"现在动会撞上并行的票"，而并行已经结束。** 四条的
原文明写着"等票 XX"或"留给下一张碰那一段的票"，而那几张票落地时没人回来接。内容上分两堆——
三条是"`status` 那一行说的话还不够准"，两条是"承载它的模块该搬家了"。

**出来的努力要有自己的名字**——它建的是什么，不是它从哪个抽屉来的。

## 那一行说的话还不够准

### Q13 —— 校验不过的那一行，外层仍说"读不到"

票 03 要求「校验不过时 `status` 显示"读取异常"，不显示数字」。不显示数字做到了；但整行读起来是

```
读不到 —— 全部 Endpoint 都没读到 —— Wired: 读取异常：电压 2000 mV 不在 …
```

"都没读到"不准：**我们读到了，只是读到的东西不可信。** 两种说法要用户做的事不同——"读不到"
多半是没插没开，"读取异常"是固件/协议对不上、或者厂商上位机在抢通道。

**它先要回答一个票 03 范围外的问题**：几条 Endpoint 各失败得不一样时，那一行说什么
（一条超时、一条读取异常）？当时不做是因为 `lost_reason()` 与 `read()` 的 `match` 正被票 05 改着。

**现状**：票 07 的 `NoReading::Display` 已经把那一行的拼装从 `run()` 里提出来、变得可测
（`src/cli/status.rs:433`），但 `Lost(reason) => "读不到 —— {reason}"` 这一层的**分类**没做。
Q34 记的"`run` 里印一句然后照常取数那一半仍然测不到"是同一格。

### Q39（尾段）—— `render` 在 `LastKnown` 时仍印"充电中 / 4235 mV"

`VeryStale` 那一档把这几样整段换掉了，理由是「『充电中』是同一句假话的另一半」。**同一条理由
对一只收进抽屉的鼠标同样成立**——那是一句现在时断言，现在只靠行尾一句"已陈旧，上次已知值"兜着。

票 08 没动它，因为那是电量/充电态/电压那一段（票 03 与票 06 的地盘），而票 08 的界是"只碰
陈旧标注那一段"。记录原话："留给下一张碰那一段的票，它值一条自己的记录。"
**已核实仍然如此**：`render` 里 `charging` / `voltage` 两个 `match` 无条件走。

同一处还挂着一笔 code review 指出的 **Data Clump**：`(reading, staleness, provenance)` 一路同行，
`render` 已经四个参数。捆成一个类型站得住，但正确形状取决于托盘那一步要什么——现在猜它等于替
第 7、8 步做决定。

### Q50 —— 草稿里的 `[device.bluetooth]` 是硬写的一段注释

票 10 落地时 `EndpointKind` 只有 `Wired` 和 `Dongle24G`（`Ble` 是票 05 的活），所以草稿里每台
设备底下那段注释掉的蓝牙占位是个常量字符串 `BLE_PLACEHOLDER`，**不经过 `draft()` 里的
`PRIORITY` 循环**。

记录给票 05 的原话：「`Ble` 进 `EndpointKind` 之后，`BLE_PLACEHOLDER` 这个常量就该退掉，改由
`draft()` 里那个 `PRIORITY` 循环连同 `commented_placeholder()` 一起产出——**那时"它在不在场"
也才真的问得出来**。」

**已核实**：`BLE_PLACEHOLDER` 还在（`src/config.rs:509`，`draft` 里 `push_str` 于 491）。
Q57（合并票 10 与票 05 时的记录）说这件事**了结了一半**：`config-refresh` 那半已经会为 `Ble`
说话了，草稿这半仍然待办。

## 承载它的模块该搬家了

### Q17 —— Endpoint 合成留在 `cli::status`，`read` / `render` 是"为了测试"才 pub

优先级循环住在 `src/cli/status.rs` 的 `read()` 里（那个文件现在 743 行），连同 `render()` 一起
是 `pub`，为的是让 `tests/endpoints.rs` 驱动得到——集成测试只看得见 pub 接口（Q3），而"拔线 →
同周期降级"在真机上拔一次线才复现一次。

spec 的「模块划分」写的是：把 Endpoint 合成搬进 `src/endpoints.rs` 变成一个真正的 pub 函数，
`cli::status` 退成只管打印。**那样 `pub` 就不是"为了测试"，而是本来如此。**

记录说"等票 06"，理由是票 06 要往这里接 Clock 与陈旧判定，"Device 模型 + Endpoint 合成 +
陈旧判定集中一处"那时才有三样东西可放、形状不用猜。
**已核实**：票 06 已 resolved，但没搬——`read()` 仍在 `src/cli/status.rs:302`。

### Q47（尾段）—— `src/config.rs` 1096 行，三个不相干的改动理由

`KNOWN_DEVICES` 这张写死的实测身份表让 `src/config.rs` 从 82 行涨到 **1096 行**。同一个文件
现在有三个不相干的改动理由：

1. 加一台设备（改这张表）
2. 改草稿文案（约 200 行用户可见的字符串常量）
3. 改写入机制（`toml_edit`）

另一条路是把表和文案各搬进自己的模块，`config.rs` 只留 schema 与读写。记录说"推荐等票 11"，
因为它要往同一个文件里加 `primary` 的回写，搬家会让它的改动落在一个刚移动过的位置上；而 spec
的「模块划分」写的是"配置读写单独一处"，一处的理由当时还站得住。
**已核实**：票 11 已 resolved，`config.rs` 1096 行。

**留表这个决定本身已定**（启发式那条路会写下错配置），不必重开。这里要磨的只有拆不拆、怎么拆。
