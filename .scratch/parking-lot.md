# Parking lot：实现过程中取过的岔路

**Status:** 长期文件 —— 本仓库每一趟队列、每一张票共用这一份
**Opened:** 2026-09-09

## 这个文件是什么

实现票据时总会撞上票没预料到、或者票写错了的地方。**其中几乎没有一件该让队列停下来。**
它们落在这里：**走最站得住脚的那条路，把岔路记下来，继续走，等条件合适时再结算。**

它不是项目的长期缺口清单。长期缺口讲的是**产品**上缺什么，由下一个动这块产品的人来读；
这份文件记的是**执行中的岔路**——票写错了、spec 没说、两份文档互相打架——由决策者在坐下来
结算一批时来读。长期缺口永远不清空，这份文件由 `/settle` 成批结算，**绝不在队列收尾时结算**。

### 什么样的事配一条记录

一条记录是**你取过的一条岔路**，不是你做过的活。三条测试，全过才写：

1. **另一条路也站得住。** 你能把它写下来，而且它不是稻草人。
   只有一条路站得住，那就没有岔路——你做的事属于 commit message，不属于这里。
2. **翻案的代价关在这张票里。** 决策者以后改主意，代价是改一处，不是把已落地的活拆掉。
   如果翻案要伸到这张票外面，那是**停线**，不是记录。
3. **你能给出推荐。** 路是你走的，你有上下文说哪条该留下。
   一条交出去只有耸肩的记录，等于把你的上下文一起弄丢了——而推迟结算的全部意义，
   就在于这批东西真被读到时结算起来很便宜。

一份把票碰过的每件事都记下来的文件是日记，决策者会像读任何人的日记一样读它：根本不读。

### 停线 —— 只有这三种

停线很贵：决策者得把整个上下文重新装回脑子。门槛：

1. **继续走会写下一个错的产物，而撤销它要伸到这张票外面。**
   典型：票的指示与上游一个仍然有效的决定相抵触。
2. **动作不可逆，而且不止一个方向站得住。**
   典型：删除或重命名一个被多处引用的东西——一个 id、一个字段、一个文件。
3. **前提不存在，票根本没法开工。** 典型："在 X 之上建 Y"，而 X 并不存在。

其余凡是过了上面三条测试的：记下来，走最站得住脚的路，继续。这包括票里的数字与你实测的
对不上、验收条件读起来含糊、票没想到的第三种情况、以及你路过的一个不相干的缺陷。

### 编号

**整份文件一条序列**，这样一条记录在做出它的 commit 里、引用它的票里、多年后结算它的那一批里
是同一个名字。一条序列碰上并行的 agent 就会撞号，所以编排者把它切成**块**：每份 brief 拿到
一小段只属于它的号。没人需要向谁要号。某个块没被用完，编号上留个空档，不花什么代价。

号里不带票号，所以 **`From:` 是必填字段**——它是唯一说明哪张票发现了这条岔路的东西。

### Q1 —— 驱动 trait 推迟到票 02 定形

**From:** 票 01（最小取数链路）

**取的路**：只落地 `Transport` 这一个 trait。鼠标驱动是模块里的自由函数
`vgn_mouse::read_battery(&dyn Transport)`，`status` 按配置里的 `driver` 字符串分发
（现在是一个 `if`）。

**另一条路**：现在就照 spec「模块划分」那一节把驱动 trait 定出来，鼠标做第一个实现。

**推荐**：保持现状。只有一个实现的 trait 形状是猜的——键盘的帧长、校验和、命令码、
响应布局全都不同，而 02 手里会同时握着两个实现，那时定的形状才有依据。翻案的代价是
一个文件加一个调用点，本来就是 02 要做的活。

### Q2 —— Transport 交换的是**不含 Report ID 的帧**

**From:** 票 01（最小取数链路）

**取的路**：`exchange()` 的入参和返回值都不含 Report ID，由 Transport 实现自己补上、
剥掉。代价是 trait 多一个 `report_id()` ——VGN 鼠标的校验和是 `0x55 − sum − report_id`，
报文编号参与了协议运算，驱动躲不开它。

**另一条路**：交换含 Report ID 的原始缓冲区。那样鼠标的校验和反而更整齐
（就是 `0x55 − sum(整个缓冲区前 16 字节)`），trait 也不需要 `report_id()`。

**推荐**：保持现状。`docs/protocol.md` 第 3 节点名"读写缓冲区第 0 字节都是 Report ID，
文档里所有下标都要 +1"是最容易一次性写错的地方——把它吸收在接缝里，正是这条接缝存在的
理由。多出来的那个 trait 方法比每个驱动各写一次 +1 便宜。

### Q3 —— 测试组织：`src/lib.rs` + `tests/` 集成测试

**From:** 票 01（最小取数链路）

**取的路**：新增 `src/lib.rs`，`main.rs` 退化成只解析命令行的薄壳。测试全部放在
`tests/` 下的集成测试里，共用的假实现与实测夹具放 `tests/common/`。

**另一条路**：不加 lib，测试写在源码里的 `#[cfg(test)] mod tests`（Rust 单元测试的默认
做法），夹具放一个 `src/` 下的 `#[cfg(test)]` 模块。

**推荐**：保持现状。spec 的 Testing Decisions 要"只测外部行为、不测私有函数"，集成测试
让编译器来守这一条（私有的东西根本看不见），而源码内测试只能靠自觉——十张票十个 agent，
自觉是会漂的。代价是多一个 `lib.rs` 和 `main.rs` 里一行 `use juicebar::cli;`。

### Q5 —— gate 在 base commit 上本来就是红的，本票顺手修了两个不属于它的文件

**From:** 票 01（最小取数链路）

**实测**：在 `6d5eb1c`（本趟队列的 base）上，gate 三条里有两条本来就不过——与本票的改动
无关，把那几个文件的原始内容单独喂给 rustfmt / clippy 验过：

- `cargo fmt --all -- --check`：`src/bluetooth.rs`（3 处）、`src/cli/caps.rs`、`src/hid.rs`
- `cargo clippy --all-targets -- -D warnings`：`src/bluetooth.rs:147`
  （`chunks_exact_to_as_chunks`）、`src/cli/probe.rs:20`（`manual_is_multiple_of`）

两条 clippy 都是 clippy 1.98 才有的新 lint，代码写下时多半是绿的——是工具链前进把它变红的，
不是谁写错了。

**取的路**：一并修掉，让 gate 真的绿。代价是本票动了两个它本不该动的文件：
`src/bluetooth.rs`（空白 + 一处 lint 等价改写）、`src/cli/caps.rs`（纯空白）。
`src/hid.rs` 也是纯空白但本票本来就在它上面搭 Transport，不算越界；
`src/cli/scan.rs` 原本就是干净的，没被碰。

**另一条路**：只格式化本票自己的文件，把那两个文件还原，在报告里把 gate 的红说清楚，
由编排者在 master 上单独来一刀。这样"只提交这张票碰过的文件"守得一丝不苟。

**推荐**：保持现状（修掉）。gate 是这趟队列的合约，红着的 gate 会被后面十张票每一张
重新撞见一次、每个 agent 重新排查一次；而这里的改动是 gate 自己的工具吐出来的，全是空白
与两行等价改写，十棵 worktree 各自跑出来的结果逐字相同，合并不会打架。
**若编排者更看重那条边界**，翻案就是还原这两个文件，代价是 gate 继续红着。

### Q16 —— 枚举接缝定成两个方法：`present()` 答在场，`open_transport()` 交 Transport

**From:** 票 04（Wired Endpoint 与优先级降级）

**取的路**：`trait Endpoints` 两个方法——`present(&Device) -> Vec<EndpointKind>` 只回答**谁在场**
（是个集合，顺序不表达任何东西），`open_transport(&Device, EndpointKind) -> Result<Box<dyn Transport>>`
交出往返用的 Transport。优先级不在接缝里，是 `EndpointKind::PRIORITY`，住在取数那一步，
于是一份假枚举没法靠调换顺序改变取数的先后。票 05 的 `Ble` 不经过驱动、也不经过 Transport，
它要在这个 trait 上再加一条自己的路；取数那一步对 `EndpointKind` **`match` 到底不写通配分支**，
所以加上第三种的那一天编译器会把人指到该改的那一行，而不是让 Ble 悄悄走上 HID 那条路。

**另一条路**：一个方法就够——`present()` 直接交出"取数的办法"，形如
`enum Readout { Hid(Box<dyn Transport>) }`，票 05 往这个 enum 上加一个 `Ble(Reading)` 变体。
那样 Ble 与 HID 的差异被收在一个类型里，trait 永远只有一个方法，加 Endpoint 种类不动 trait。
代价是今天就得为一个只有一个变体的 enum 付出类型和构造的噪音，而且在场判断与开通道被绑成
一次操作——想只问"谁在场"而不打开任何东西就做不到了（票 07 的"暂停"多半正想这么问）。

**推荐**：保持现状（两个方法）。理由是"在场"和"打开"确实是两个问题，票 07 要在**不打开**
的前提下把 Wired 与 Dongle24G 标成暂停，把它们绑死会让那张票先来拆一次。翻案的代价是
一个 trait、一个假实现、一个调用点，都在本票范围内。

### Q17 —— Endpoint 合成留在 `cli::status`，并把 `read` / `render` 放成 `pub`

**From:** 票 04（Wired Endpoint 与优先级降级）

**取的路**：优先级循环仍住在 `src/cli/status.rs` 的 `read()` 里，连同 `render()` 一起改成 `pub`，
好让 `tests/endpoints.rs` 驱动得到——集成测试只看得见 pub 接口（Q3），而"拔线 → 同周期降级"

**另一条路**：照 spec「模块划分」那一节，把 Endpoint 合成搬进 `src/endpoints.rs` 变成一个真正的
pub 函数，`cli::status` 退成只管打印。那样 `pub` 就不是"为了测试"而是本来如此。

**推荐**：等票 06。搬家现在做撞得最狠——票 02 此刻正在 `read()` 里改驱动分发，把这个函数整个

翻案的代价是把两个函数连同它们的用例挪一次，关在本票和 06 之间。

### Q18 —— 驱动分发从 `read()` 原样搬进 `read_with_driver()`

**From:** 票 04（Wired Endpoint 与优先级降级）

**这条记录主要是给合并的人看的，不是给结算的人看的。**

**取的路**：`read()` 只管 Endpoint 的优先级与降级；那句
`if device.driver != "vgn_mouse" { bail!("驱动 {} 尚未实现", device.driver); }`
连措辞一起原样搬进新的 `read_with_driver(device, endpoint, transport)`，一个字没改。函数上方写了
一句注释点明"驱动分发只在这个函数里做，`read()` 里不再做"。多出来的 `_endpoint` 参数本票没人用，
它是给驱动那一维的：一个驱动要覆盖该家族的所有 Endpoint 种类，键盘的 Dongle24G 与 Wired 命令不同。

**为什么值得记**：票 02 此刻正在**原来那个 `read()` 里**把同几行改写成两个驱动的分发，它不知道
`read_with_driver` 会存在。git 看到的是"一边改这几行、另一边把这几行整块搬走"——这种形状最坏的
结果不是冲突，是**自动合并"成功"而结果是错的**：02 的分发留在 `read()` 里，而 `read()` 已经不做
驱动分发了，键盘于是静默走不到驱动，两边的测试各自还都绿着。合并时正确的归宿是
`read_with_driver`。

**另一条路**：驱动分发原地不动留在 `read()` 里，只把 Endpoint 循环抽成一个函数。那样 02 的改动
落在原处，合并是干净的；代价是两维揉在同一个函数里，加驱动和加 Endpoint 都改同一处。

**推荐**：保持现状（搬走）。两维正交是这张票守边界的全部依据，揉回去等于把边界交还给运气；
而这条记录本身就是合并的说明书，风险由它兜住。翻案是把那三行搬回 `read()`，关在本票内。

### Q19 —— 驱动没实现的 Device，那一行不再说"尚未实现"，改说"一条 Endpoint 都不在场"

**From:** 票 04（Wired Endpoint 与优先级降级）

**实测**：拿仓库那份 `config.example.toml` 跑 `status`，键盘那一行本票前后变了：

```
改之前：VGN Neon75  读不到 —— 驱动 vgn_keyboard 尚未实现
改之后：VGN Neon75  读不到 —— 配置的 Endpoint（Dongle24G）一条都不在场：
                              本机枚举不到它们能发输出报文的通路（设备没插？）
```

原因是顺序换了：驱动检查以前在最前面，现在在 Endpoint 选完之后才轮到；而键盘的 vendor
collection 实测 `in:0 out:0 feat:65`，被"限于能发输出报文的"那道筛子筛掉，于是先撞上的是
"不在场"。**键盘当时是插着的**，所以这句话不能只说"设备没插"——`find_output_collection`
的函数注释早就点名过这个坑（"否则报出来的是一句误导人的『设备没插』"），本票只是让键盘也踩上了。
措辞已经改成先说清查的是什么，把没插降格成一个问句，所以它现在不说假话了；
但它仍然没有"驱动尚未实现"那么切中要害。

**另一条路**：把驱动检查提回 `read()` 的最前面，Endpoint 循环之后置。这样"尚未实现"照旧，
代价是驱动分发又回到 `read()` 里——正是 Q18 刚搬走的东西，两处都留就更糟。

**推荐**：保持现状，等票 02。它一落地，键盘就有真驱动、也会带来 feature 报文那条 Transport，
这一行两个毛病一起消失（驱动名认得、通路也找得到），届时这条记录直接作废。若票 02 迟迟不落地
而这一行碍事，翻案就是把三行检查搬回 `read()`，关在本票内。

### Q46 —— `toml_edit` 在本票就收进来（票 11 的第一条框变成"确认已引入"）

**From:** 票 10（配置自举与 config-refresh）

**这条一定要读：它直接改变票 11 的活。** 票面的依赖边是 11 依赖 10，但能力上 10 需要 11
的第一条框（"引入格式保留的 TOML 编辑能力"）。

**取的路**：本票就把 `toml_edit 0.25.13` 收进 `Cargo.toml`（按仓库惯例写明收它的理由），
`config-refresh` 直接用它做原地编辑。**票 11 那条框到时候变成"确认已引入"，不是重新做一遍。**

**另一条路**（brief 里的路 B）：本票只做"首次生成草稿"——新文件不需要格式保留，手写模板就够；
`config-refresh` 的"只填空缺"改用追加式（在文件末尾补缺的块）或者只在命令行打印该补什么。

**推荐**：保持现状（收 `toml_edit`）。**追加式那条路是错的，不只是差**：TOML 里
`[device.wired]` 属于它前面最近的那个 `[[device]]`，追加到文件末尾就等于把这条 Endpoint 挂到
**最后一台**设备头上——两台设备的配置里，键盘的有线身份会落到鼠标名下，而文件照样解析得动，
错误直到取数时才以一句"读不到"的面目出现。只在命令行打印那条路避开了这个坑，但也就把票面
第 3、4 条框（"扫描并填充"）降级成了"告诉用户自己贴"。
`toml_edit` 用起来是顺的：把块渲染成文本再解析回来，`vid = 0x391D` 的十六进制写法原样保住
（它保留解析时看到的 repr），不必手工构造 `Formatted<i64>` 再改 repr。
翻案的代价是一条依赖和 `insert_endpoint_block` 一个函数，关在本票内。

**踩到的一个坑，记在这里给票 11**：从"片段文档"里克隆出来的 `Table` **带着它在片段里的
`doc_position`**，搬进主文档后会按那个位置排序，于是块落到错的 `[[device]]` 底下。必须
`set_position(None)`，让它继承父表的位置。`src/config.rs` 的 `insert_endpoint_block` 里有一段
注释写了这件事，`tests/config.rs::config_refresh_puts_the_block_under_the_right_device` 抓它。
票 11 回写 `primary` 是改一个已有的标量，碰不到这个坑；但它若要新插入什么表，会原样撞上。

### Q47 —— 认设备靠一张写死的实测身份表 `KNOWN_DEVICES`，不靠推断

**From:** 票 10（配置自举与 config-refresh）

**取的路**：`src/config.rs` 里一张 `KNOWN_DEVICES` 常量表，逐台写死 id / name / driver /
两条 HID Endpoint 的身份 / "Wired 怎么才会出现"那句提示。自举时"扫到表里某台设备的任一条
身份"才写出 `[[device]]`；`config-refresh` 先看这台 Device **已配好的身份**和表里哪一条对上
（那是证据），一块都没配时才退到比 `id`。表里没有的 vendor collection 只列身份，不猜。

**另一条路**：不要这张表。自举时把扫到的 vendor collection 全列成注释掉的候选，`driver`、
`id`、哪条是 Wired 哪条是 Dongle24G 全由用户填；`config-refresh` 用"同 VID 且未被登记"这类
启发式来猜缺的块。

**推荐**：保持现状（留表）。启发式那条路会**写下错配置**：同一家厂商出两件外设时 VID 相同
（本仓库这两台恰好不同，所以这个坑今天不显形），张冠李戴的身份写进文件后照样解析得动。
而没有表则连票面第 1 条"能猜的先猜"和第 3 条"扫描并填充空着的块"都做不到——填一块的前提就是
知道这台设备那条 Endpoint 长什么样。代价是加一台设备要改一次代码而不是只改配置；对一个
单人自用工具，这笔账划得来，而且表就在 `src/config.rs`，加一条是十几行数据。
翻案的代价是删掉一个常量和 `recognise()`，关在本票内。

**这张表让 `src/config.rs` 从 82 行涨到 700 行**，同一个文件现在有三个不相干的改动理由：
加一台设备（改这张表）、改草稿文案（约 200 行用户可见的字符串常量）、改写入机制（`toml_edit`）。
另一条路是把表和文案各搬进自己的模块，`config.rs` 只留 schema 与读写。**推荐等票 11**：
它要往同一个文件里加 `primary` 的回写，搬家现在做会让它的改动落在一个刚移动过的位置上；
而 spec 的「模块划分」写的是"配置读写单独一处"，一处的理由今天还站得住。

**顺带记一笔**：表里 `neon75` 的 Wired（`3151:502F`）**至今没有实测过**——键盘要把机身模式
开关拨到有线档才枚举得出来。它写下去不会造成错配置：草稿里它是注释掉的占位，而
`config-refresh` 只在本机真的枚举得到这组 VID/PID/usage 时才把它填成真块。`report_id = 0`
是照它的 Dongle24G 抄的，那一条实测确实是 0。

### Q48 —— 没有配置时 `status` 自己生成草稿，而不是打发用户去跑另一条命令

**From:** 票 10（配置自举与 config-refresh）

**取的路**：`src/cli/status.rs` 里那句"没找到配置，抄 config.example.toml 过去"换成调用
`config_refresh::bootstrap(&path)`——扫一遍本机、写出草稿、印一段"注释掉的块要你看一眼"，
这一趟就结束，不接着取数。票面第 1 条的原话是"首次运行且无配置时生成带注释的草稿"，
而 `config.example.toml` 的开头也早就写着"首次运行时程序会扫描本机、生成一份带注释的草稿"。

**另一条路**：`status` 只把话改成"跑 `juicebar config-refresh` 生成一份草稿"，生成这件事只
由那条命令做。这样 `status` 严格只读，不会因为一次手滑打错 `--config` 路径就在别处落一个文件。

**推荐**：保持现状（自动生成）。两处对"配置在哪"只有一个答案（`cli::default_config_path`），
而首次运行本来就是这个工具最需要把人接住的一刻。落盘那一步用的是 `create_new`，绝不覆盖已有
文件。**注意这处改动碰了 `status.rs`**：只碰了 `!path.exists()` 那个分支和 import，
`read()` / `read_with_driver()` / `render()` 一个字没动（票 02 正在改那三个）。
翻案的代价是那四行换回一句 `bail!`，关在本票内。

### Q49 —— `config-refresh` 不清理它自己在草稿里留下的注释掉的占位

**From:** 票 10（配置自举与 config-refresh）

**取的路**：补上真块之后，草稿里那段"这条 Endpoint 现在扫不到 + 注释掉的身份"**留在原地**。
草稿里那段话因此是这么写的："到那时这几行就只是历史记录了，留着或删掉都行"——所以它在补全
之后并不说假话。实测出来的样子是真块排在占位注释**上面**（占位挂在它后面那个东西的
decor 前缀里），读起来是"这一块补上了，下面这段是它当初为什么缺"。

**另一条路**：`config-refresh` 顺手把它认得的占位注释删掉。`toml_edit` 里那几行注释住在
后一个 item 的 decor 前缀里，按标记逐行筛掉是做得到的，几十行。

**推荐**：保持现状（不删）。ADR-0003 的边界是"绝不修改用户已经写过的值"，而注释同样是用户
可能改过的东西——占位是程序写的，但用户完全可能在那几行里加了自己的一句话。让程序**永不删除
文件里任何一个字符**是这条边界最省心的守法，代价只是一段变成历史记录的注释。
若嫌它碍事，翻案就是加一个"删掉带标记的占位段"的函数，关在本票内。

**同一条边界的另一面：`config-refresh` 也不新增 `[[device]]`。** 它只往已有的
`[[device]]` 里补空着的块。代价是一个真实的死角：首次运行时一台设备都没插（正是本票预设的
常态）→ 草稿里零个 Device → 插好之后跑 refresh 只会说"没有需要补的空缺"。**已经处理的部分**是
把草稿里那句话改成真话——空草稿现在写着"把这个文件删掉再跑一次"，而那个文件里没有任何用户
写过的东西，删掉不损失什么（`NOTHING_RECOGNISED`）。

**另一条路**：refresh 也补 Device——本机扫到、而配置里没有的表内设备，整条 `[[device]]` 补进去。
渲染那一段现成（`draft` 里的循环），插入走 `ArrayOfTables::push`。**推荐暂不做**：它会和"用户
故意删掉一台设备"打架——那位用户每跑一次 refresh 就被塞回来一次，而程序分不出这两种情形。
票面第 3 条框的原话是"填充空着的**块**"，一整台 Device 不是一个空着的块。真要做，翻案的代价是
一个渲染函数加一次 push，关在这张票的范围内。

### Q50 —— 草稿里的 `[device.bluetooth]` 是硬写的一段注释，不走 `EndpointKind`

**From:** 票 10（配置自举与 config-refresh）

**取的路**：草稿里每台设备底下都有一段注释掉的 `[device.bluetooth]` 占位，写明"MAC 猜不出来
（BLE 射频是另一颗芯片，VID 都和 dongle 不同），跑 `juicebar scan` 看蓝牙那一段抄过来"。
它是一个常量字符串，**不经过 `EndpointKind::PRIORITY` 那个循环**——那个枚举眼下只有 `Wired`
和 `Dongle24G`，`Ble` 是票 05 的活。

**另一条路**：干脆不写。Ble 整条属于票 05，本票不提它，等 05 落地时连草稿一起加。

**推荐**：保持现状（写出来）。票面的重点原话是"用户不该在不知情的情况下缺一整条 Endpoint"，
而 Ble 正是三条之一；一声不吭地不提它，用户就不知道自己少了一条。
**给票 05 的提示**：`Ble` 进 `EndpointKind` 之后，`BLE_PLACEHOLDER` 这个常量就该退掉，改由
`draft()` 里那个 `PRIORITY` 循环连同 `commented_placeholder()` 一起产出——那时"它在不在场"
也才真的问得出来（现在问不出来，所以它只能是注释）。`src/config.rs` 里那个常量的文档注释
写了这件事。翻案的代价是删一个常量和一处 `push_str`，关在本票内。
