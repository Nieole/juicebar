# Parking lot：实现过程中取过的岔路

**Status:** 长期文件 —— 本仓库每一趟队列、每一张票共用这一份
**Opened:** 2026-09-09

## 这个文件是什么

实现票据时总会撞上票没预料到、或者票写错了的地方。**其中几乎没有一件该让队列停下来。**
它们落在这里：**走最站得住脚的那条路，把岔路记下来，继续走，等条件合适时再结算。**

它不是项目的长期缺口清单。长期缺口讲的是**产品**上缺什么，由下一个动这块产品的人来读；
这份文件记的是**执行中的岔路**——票写错了、spec 没说、两份文档互相打架——由决策者在坐下来
结算一批时来读。长期缺口永远不清空，这份文件由 `/settle` 成批结算，**绝不在队列收尾时结算**。

### 什么样的事配一条记录

一条记录是**你取过的一条岔路**，不是你做过的活。三条测试，全过才写：

1. **另一条路也站得住。** 你能把它写下来，而且它不是稻草人。
   只有一条路站得住，那就没有岔路——你做的事属于 commit message，不属于这里。
2. **翻案的代价关在这张票里。** 决策者以后改主意，代价是改一处，不是把已落地的活拆掉。
   如果翻案要伸到这张票外面，那是**停线**，不是记录。
3. **你能给出推荐。** 路是你走的，你有上下文说哪条该留下。
   一条交出去只有耸肩的记录，等于把你的上下文一起弄丢了——而推迟结算的全部意义，
   就在于这批东西真被读到时结算起来很便宜。

一份把票碰过的每件事都记下来的文件是日记，决策者会像读任何人的日记一样读它：根本不读。

### 停线 —— 只有这三种

停线很贵：决策者得把整个上下文重新装回脑子。门槛：

1. **继续走会写下一个错的产物，而撤销它要伸到这张票外面。**
   典型：票的指示与上游一个仍然有效的决定相抵触。
2. **动作不可逆，而且不止一个方向站得住。**
   典型：删除或重命名一个被多处引用的东西——一个 id、一个字段、一个文件。
3. **前提不存在，票根本没法开工。** 典型："在 X 之上建 Y"，而 X 并不存在。

其余凡是过了上面三条测试的：记下来，走最站得住脚的路，继续。这包括票里的数字与你实测的
对不上、验收条件读起来含糊、票没想到的第三种情况、以及你路过的一个不相干的缺陷。

### 编号

**整份文件一条序列**，这样一条记录在做出它的 commit 里、引用它的票里、多年后结算它的那一批里
是同一个名字。一条序列碰上并行的 agent 就会撞号，所以编排者把它切成**块**：每份 brief 拿到
一小段只属于它的号。没人需要向谁要号。某个块没被用完，编号上留个空档，不花什么代价。

号里不带票号，所以 **`From:` 是必填字段**——它是唯一说明哪张票发现了这条岔路的东西。

### Q1 —— 驱动 trait 推迟到票 02 定形

**From:** 票 01（最小取数链路）

**取的路**：只落地 `Transport` 这一个 trait。鼠标驱动是模块里的自由函数
`vgn_mouse::read_battery(&dyn Transport)`，`status` 按配置里的 `driver` 字符串分发
（现在是一个 `if`）。

**另一条路**：现在就照 spec「模块划分」那一节把驱动 trait 定出来，鼠标做第一个实现。

**推荐**：保持现状。只有一个实现的 trait 形状是猜的——键盘的帧长、校验和、命令码、
响应布局全都不同，而 02 手里会同时握着两个实现，那时定的形状才有依据。翻案的代价是
一个文件加一个调用点，本来就是 02 要做的活。

### Q2 —— Transport 交换的是**不含 Report ID 的帧**

**From:** 票 01（最小取数链路）

**取的路**：`exchange()` 的入参和返回值都不含 Report ID，由 Transport 实现自己补上、
剥掉。代价是 trait 多一个 `report_id()` ——VGN 鼠标的校验和是 `0x55 − sum − report_id`，
报文编号参与了协议运算，驱动躲不开它。

**另一条路**：交换含 Report ID 的原始缓冲区。那样鼠标的校验和反而更整齐
（就是 `0x55 − sum(整个缓冲区前 16 字节)`），trait 也不需要 `report_id()`。

**推荐**：保持现状。`docs/protocol.md` 第 3 节点名"读写缓冲区第 0 字节都是 Report ID，
文档里所有下标都要 +1"是最容易一次性写错的地方——把它吸收在接缝里，正是这条接缝存在的
理由。多出来的那个 trait 方法比每个驱动各写一次 +1 便宜。

### Q3 —— 测试组织：`src/lib.rs` + `tests/` 集成测试

**From:** 票 01（最小取数链路）

**取的路**：新增 `src/lib.rs`，`main.rs` 退化成只解析命令行的薄壳。测试全部放在
`tests/` 下的集成测试里，共用的假实现与实测夹具放 `tests/common/`。

**另一条路**：不加 lib，测试写在源码里的 `#[cfg(test)] mod tests`（Rust 单元测试的默认
做法），夹具放一个 `src/` 下的 `#[cfg(test)]` 模块。

**推荐**：保持现状。spec 的 Testing Decisions 要"只测外部行为、不测私有函数"，集成测试
让编译器来守这一条（私有的东西根本看不见），而源码内测试只能靠自觉——十张票十个 agent，
自觉是会漂的。代价是多一个 `lib.rs` 和 `main.rs` 里一行 `use juicebar::cli;`。

### Q5 —— gate 在 base commit 上本来就是红的，本票顺手修了两个不属于它的文件

**From:** 票 01（最小取数链路）

**实测**：在 `6d5eb1c`（本趟队列的 base）上，gate 三条里有两条本来就不过——与本票的改动
无关，把那几个文件的原始内容单独喂给 rustfmt / clippy 验过：

- `cargo fmt --all -- --check`：`src/bluetooth.rs`（3 处）、`src/cli/caps.rs`、`src/hid.rs`
- `cargo clippy --all-targets -- -D warnings`：`src/bluetooth.rs:147`
  （`chunks_exact_to_as_chunks`）、`src/cli/probe.rs:20`（`manual_is_multiple_of`）

两条 clippy 都是 clippy 1.98 才有的新 lint，代码写下时多半是绿的——是工具链前进把它变红的，
不是谁写错了。

**取的路**：一并修掉，让 gate 真的绿。代价是本票动了两个它本不该动的文件：
`src/bluetooth.rs`（空白 + 一处 lint 等价改写）、`src/cli/caps.rs`（纯空白）。
`src/hid.rs` 也是纯空白但本票本来就在它上面搭 Transport，不算越界；
`src/cli/scan.rs` 原本就是干净的，没被碰。

**另一条路**：只格式化本票自己的文件，把那两个文件还原，在报告里把 gate 的红说清楚，
由编排者在 master 上单独来一刀。这样"只提交这张票碰过的文件"守得一丝不苟。

**推荐**：保持现状（修掉）。gate 是这趟队列的合约，红着的 gate 会被后面十张票每一张
重新撞见一次、每个 agent 重新排查一次；而这里的改动是 gate 自己的工具吐出来的，全是空白
与两行等价改写，十棵 worktree 各自跑出来的结果逐字相同，合并不会打架。
**若编排者更看重那条边界**，翻案就是还原这两个文件，代价是 gate 继续红着。

### Q6 —— 驱动 trait 抽了，形状是「报文种类 + 取一次电量」，不带 Endpoint 种类参数

**From:** 票 02（键盘驱动）—— 结算 Q1

**取的路**：`sources::Driver` 两个方法：`report_kind()` 说这个协议家族走 output+input 还是
feature（超时挂在前者上，它是协议的性质），`read_battery(&dyn Transport)` 取一次数。
配置里的 `driver` 字符串经 `sources::driver_for(name) -> Option<&'static dyn Driver>` 落到
`VgnMouse` / `VgnKeyboard` 两个单元结构上，这是全项目唯一一处驱动名到实现的映射。
协议逻辑仍是各模块里的自由函数，trait 只做分发。

**另一条路**（两条，都站得住）：

1. 不抽，`status::read()` 里改成一个两臂 `match`。两个实现还撑不起一个 trait。
2. 抽，但带上 Endpoint 种类参数（`read_battery(transport, endpoint_kind)`），照 spec
   「模块划分」写的"一个驱动覆盖该家族的所有 Endpoint 种类，内部按种类分支"。

**推荐**：保持现状。对 (1)：报文种类必须由某处按驱动分流——键盘的 vendor collection 是
`in:0 out:0 feat:65`，拿 output 的条件去找它报出来的是一句误导人的"设备没插"。不抽 trait，
这件事就得在 `status` 里跟"发什么命令"各分流一次，同一个字符串被 match 两遍，两处迟早
走样。对 (2)：**键盘有线本体 `0x82` 至今没实测过**（spec 明确列为 Out of Scope，
`docs/protocol.md` 第 7 节还挂着"用正确帧重测"），现在定参数形状，定的是没人验过的那一半；
而鼠标两种 Endpoint 命令相同，票 04 加 `Wired` 时这个 trait 原封不动就能用。等 `502F` 真读
出数了再加参数，代价是一个 trait 方法加两个实现——比现在猜错了再拆便宜。
**后面九张票照这个形状写。**

### Q7 —— `Reading.voltage_mv` 改成 `Option<u16>`（**波及票 03 与票 04**）

**From:** 票 02（键盘驱动）

**这一条不是留给将来结算的**，是留给合并这一批的人和票 03 的 agent 当场读的。

**不是停线**：改一个被多处引用的公共字段本该按停线上报（准入规则里的判据 2），本票在动手**之前**
就把这条岔路和它的波及面报给了编排者，编排者当场认可了类型改动、并指定了落地方式
（`render()` 只做类型适配的最小改动、单独成块、波及面写进这条记录）。所以决定已经做过了，
这里记的是决定本身，不是一个待批的请求。

**取的路**：`Reading.voltage_mv: u16` → `Option<u16>`。键盘的 `0xF7` 回包里根本没有电压这一项，
鼠标那边照旧包成 `Some(...)`。

**另一条路**：保持 `u16`，键盘填 `0`。改动面小得多，一个文件都不用碰。

**推荐**：保持现状。`0` 不是"没有电压"，它是一个会被下游当真的数字：spec 定的合理性校验是
`voltage ∈ 3050..=4350`，拿 0 顶上去会把**每一条**键盘读数判成"读取异常"；而 `level_source =
"auto"` 在电压 ≤ 4110 时要走 Derived Level，0 mV 查表会算出一个理直气壮的 0%——把键盘显示成
空电。这正是这个项目一路在防的"看着合理但其实是编的数字"。

**波及面（这条记录存在的理由）**：

- **票 03（合理性校验与 level 来源）**：电压值域校验和 `auto` 分流都要按 `None` 分支写——
  没有电压时不校验电压、也不可能有 Derived Level，只能取 Reported Level。这不是额外的活，
  是这张票本来就要面对的键盘现实，只是类型现在把它摆到了明面上。
- **票 04（Wired Endpoint 与优先级降级）**：`src/cli/status.rs` 的 `render()` 里印电压那一格
  被改成了一个 `match reading.voltage_mv`，`None` 时整格不印。**只动了这一处**，函数的其余部分
  和输出措辞一个字没碰，好让票 04 在同一个函数里加来源标注时冲突是机械可解的。

### Q8 —— 键盘的充电位交 `None`，`Reading.charging` 因此也成了 `Option<bool>`（**同样波及票 04**）

**From:** 票 02（键盘驱动）

**取的路**：`charging: None`，并把 `Reading.charging` 由 `bool` 改成 `Option<bool>`；
`render()` 里说不上来时那一格整个不印。鼠标那边照旧包成 `Some(...)`（它这一位已校准）。

**另一条路**：照 `docs/protocol.md` 解析 `[9]`（`Some(frame[9] != 0)`），保持 `charging: bool`。
**本票一度就是这么写的**，理由是"`[9]` 是 HUB 源码写明的字段，实测到的 `00` 与『满电、已不再
充电』自洽，硬编 false 反而多做一个断言"。

**推荐**：现状（`None`）。上面那条理由有个洞，是 code review 的 spec 轴抓出来的：它假定
"暂不显示充电态"由呈现层负责，而 `render()` 是**无条件**印"未充电 / 充电中"的——只要驱动交出
一个 `bool`，界面上就必定显示一个没人验过的断言。spec 的 Out of Scope 写着「键盘 `charging`
位的验证……**键盘暂不显示充电态**」，`docs/protocol.md` 第 7 节也仍把 `[9]` 挂在待实测清单上
（实测期间电池一直满电，从没抓到过 `!= 0`）。`None` 让"不知道"在类型上就说得出来，和 Q7 的
电压是同一个道理：**没验过的位当成 false 交出去，下游再也分不清"确实没充电"和"我不知道"。**

**波及面**：与 Q7 同一处——`src/cli/status.rs` 的 `render()` 多一个 `match reading.charging`
的独立分支（同样只动那一格）。翻案是把 `None` 换回 `Some(frame[9] != 0)`，两行；真要复测，
得等键盘电量掉下来。

### Q9 —— 键盘回包里没有 cmd 回显可校验，改用严格的就绪标志挡住残留帧

**From:** 票 02（键盘驱动）

**票面与协议对不上**。票 02 的验收框写着「校验回包的 cmd 回显；该缓冲区保存的是"最近一次
应答"，不校验就可能把上一条命令的结果当成本次的」。危险是真的，但 **`0xF7` 的回包里没有
cmd 回显这个字段**：`docs/protocol.md` 第 2 节写明 `[0]` 是就绪标志、`[1]` 是 level、`[9]` 是
charging，第 7 节还确认"HUB 只用了 `[0]`/`[1]`/`[9]`"。鼠标那边 `[0]` 才是 cmd 回显，两条协议
在这一位上正好不同。

**取的路**：把就绪标志当成真正的标志位——`[0] == 0` 判未就绪（重试），`[0] == 1` 才采信，
**其余取值一律判成"这一帧不是本次请求的应答"**。这比 HUB 严：HUB 只判 `result[0] == 0`，
非零一律当就绪。严的这一点正好承担了票要的那件事：第 7 节记着实测抓到过一帧残留
`00 | F4 01 F4 01 …`（HUB 拉设备信息时留在共享缓冲区里的，小端 `0x01F4` = 500），
剥掉 Report ID 后它的 `[0]` 是 `0xF4`——"非零即就绪"会把它放行，读出一个理直气壮的 1%。
夹具 `KEYBOARD_STALE_RESIDUE` 和用例 `rejects_a_response_left_over_from_another_command`
守的就是这条。

**另一条路**：照 HUB 写，只判 `== 0`，把"认出别人的应答"整个留给票 03 的合理性校验。

**推荐**：保持现状。留给票 03 挡不住这一帧——`level = 1` 落在 `0..=100` 里，值域校验放行，
而键盘的回包既没有电压也没有校验和可以对，票 03 手上没有别的字节能用来否决它。翻案是
把那个 `if` 删掉，一行，代价关在这张票里。
**若某天固件让 `[0]` 有了 `1` 以外的合法取值**，这里会开始误报"不是本次应答"，那时把
`READY` 放宽即可，报错信息已经把读到的值印出来了。

**这条挡不住的那一半，得说明白**（code review 的 spec 轴提的）：如果残留帧的 `[0]` 恰好就是
`0x01`，它与一份真应答**在字节上不可区分**——`0xF7` 的回包既没有 cmd 回显、也没有校验和，
协议本身没留下任何能否决它的字节。目前只能靠"每次取数都紧接着自己发的那一条命令读"来降低
概率，以及 spec 定的"检测到厂商上位机在跑就暂停 HID 轮询"（那才是这块共享缓冲区被别人写脏的
主要来源）。**这不是本票能修的**，记在这里是为了别让人以为就绪标志把这件事关严了。

### Q10 —— 键盘闲置后 dongle 会连着多次答未就绪，重试上界取 10 次是个猜测的够用值

**From:** 票 02（键盘驱动）

**实测**（本票落地时，对着真硬件）：`status` 第一次跑，鼠标读到 100% / 4131 mV，键盘却
`读不到 —— dongle 连着 3 次都报未就绪`。用 `probe` 单发正确帧复核，回读是
`00 | 00 64 00 00 01 01 01 …`——**正好是票点名的那条未就绪夹具**，`[0] == 0` 而 `[1]`
照样躺着一个 `0x64`。连发 6 次一次性轮询全是未就绪，第 7 次转为
`00 | 01 64 00 00 01 01 01 …`（`docs/protocol.md` 实测记录里那一帧），此后 `status`
连跑三次都稳定读到 100%。

也就是说：**键盘闲置后需要好几秒的轮询才会就绪**，而不是文档"实测首读就命中"所暗示的
那样。原先取 3 次（约 200 ms）在这种冷启动下必然失败。

**取的路**：`READY_ATTEMPTS` 由 3 提到 10（约 900 ms）。理由是它仍远小于 Dongle24G 的
60 秒轮询间隔，且与鼠标那条 3000 ms 读超时同一数量级——两者等的是同一件事。

**另一条路**：给键盘一个和鼠标对等的整 3000 ms 预算（30 次 × 100 ms），冷启动几乎必中。

**推荐**：先按 10 走，把这条留给拥有轮询周期的那张票定案。理由：**这个上界该由谁付代价，
不是驱动能单独决定的。**spec 定的取数流程是 `Wired > Dongle24G > Ble` 依次尝试、
"靠前的 Endpoint 失败时在同一个轮询周期内立刻降级"——键盘在 Dongle24G 上多阻塞一秒，
就是 `Ble` 那条兜底晚一秒才被尝试。而 Endpoint 优先级与降级是**票 04** 的活，陈旧判定
与轮询间隔是再往后的票。驱动这边只该保证"有界、且错误说得清"，两条都已做到。
翻案就是改一个常量，代价关在一行里。

**副作用要留意**：延迟是驱动里一个硬编的 `thread::sleep`，所以这个上界直接决定
`refuses_to_read_a_battery_out_of_a_frame_that_is_never_ready` 那条用例的耗时——现在
10 次 × 100 ms，整个键盘测试目标由 0.00 s 变成 **0.90 s**。code review 的 standards 轴点出
spec 设 Clock 接缝正是为了"测试不需要 sleep"，说得对；本票没把它做成可注入的，是因为 Clock
接缝至今没有哪张票落地过，而为一个常量提前发明它属于猜形状（同 Q6 的理由）。真要把上界提到
30 次（近 3 秒），就该先把延迟做成可注入的，而不是让测试跟着睡。

**另一个没取的旋钮**：HUB 的 `getDongleData()` 是**每次发命令之前**都 `sleep(100)`，包括头一次；
本实现只在重试之间等。键盘醒着时首读即就绪，那 100 ms 是白搭的延迟，所以没照抄。若日后发现
冷启动首读几乎必然未就绪，把这个 sleep 补到首发之前，比加大上界更省。
